    7. Delegates, lambda's en gebeurtenissen

    In de cursus van 2008 volgde dit hoofdstuk op het hoofdstuk over grafische gebruikersinterfaces met Windows Forms: gebeurtenissen werden eerst geïntroduceerd in de context van knoppen en formulieren, waarna studenten leerden hoe ze gebeurtenissen in hun eigen klassen konden maken. Het hoofdstuk over grafische gebruikersinterfaces is uit deze versie van de cursus verwijderd. We beginnen daarom direct met het concept dat aan het hele mechanisme ten grondslag ligt: de delegate, dat wil zeggen een object dat naar een of meer methoden verwijst. Alle voorbeelden zijn consoleprogramma's.

    In de afgelopen twintig jaar zijn delegates een van de meest gebruikte hulpmiddelen van de taal geworden. Ze schrijven is aanzienlijk eenvoudiger geworden dankzij lambda-expressies (C# 3), die we al — zonder in detail te treden — met LINQ in hoofdstuk 5 hebben gebruikt: [Where(n => n > 5)] geeft een lambda — en dus een delegate — door aan de methode [Where]. Dit hoofdstuk legt uit wat er achter deze syntaxis schuilgaat. Het sluit af met gebeurtenissen, die eveneens op delegates zijn gebaseerd. De grafische gebruikersinterfaces van .NET (Windows Forms, WPF, .NET MAUI) en de webframeworks zijn op dit mechanisme gebaseerd: een klik op een knop of de komst van een HTTP-aanvraag wordt gesignaleerd aan geabonneerde methoden.

    De programma's in dit hoofdstuk zijn single-file-applicaties in de map [07-delegates]. Ze worden uitgevoerd met [dotnet run delegates-NN.cs].

    7.1. Voorgedefinieerde delegatetypen

    7.1.1. Het concept van een delegate

    Een delegatetype beschrijft een model (ook wel prototype of signatuur genoemd) van een methode: de typen van de parameters en het type van de retourwaarde. Een variabele van een delegatetype kan dan naar elke methode verwijzen die aan dit model voldoet en deze uitvoeren.

    Het .NET Framework definieert tal van delegatetypen. Het oudste is [EventHandler], dat wordt gebruikt door alle gebeurtenissen die we aan het einde van dit hoofdstuk bespreken. Het is als volgt gedefinieerd:

    1
    public delegate void EventHandler(object? sender, EventArgs e);

    Het sleutelwoord [delegate] maakt van [EventHandler] een delegatetype. Dit type duidt een methodepatroon aan:

    • waarvan de eerste parameter een object van het type [object?] is (het object dat de gebeurtenis heeft veroorzaakt, mogelijk [null]);
    • waarvan de tweede parameter een object van het type [EventArgs] is (informatie over de gebeurtenis);
    • die geen resultaat teruggeeft ([void]).

    Een methode die overeenkomt met het model dat door [EventHandler] wordt gedefinieerd, kan er als volgt uitzien:

    1
    static void Display(object? sender, EventArgs e) { ... }

    Om een object van het type [EventHandler] te maken dat naar deze methode verwijst, kunt u schrijven:

    1
    EventHandler handler = new EventHandler(Display);

    of, eenvoudiger:

    1
    EventHandler handler = Display;

    In deze tweede notatie wordt de methodenaam [Display] (een methodegroep, aangezien een methode meerdere overloads kan hebben) door de compiler automatisch omgezet in een object [EventHandler]: dit heet methodegroepconversie, wat sinds C# 2 mogelijk is. De compiler kiest uit de overloads van [Display] degene die bij de signatuur van de delegate past. De delegate wordt vervolgens als een methode uitgevoerd: [handler("program", EventArgs.Empty)].

    7.1.2. De generieke delegates Func, Action en Predicate

    Vóór generics (C# 2) moest voor elke methodesignatuur een delegatetype worden gedefinieerd. Tegenwoordig biedt het framework generieke delegatetypen die vrijwel alle behoeften dekken:

    Delegatetype
    Methoden waarnaar wordt verwezen
    [Action]
    Geen parameters, geen retourwaarde: [void M()]
    [Action<T1, ..., T16>]
    1 tot 16 parameters, geen resultaat: [void M(T1 p1, ...)]
    [Func<TResult>]
    Geen parameters, één resultaat: [TResult M()]
    [Func<T1, ..., T16, TResult>]
    1 tot 16 parameters, een resultaat van het type [TResult] (altijd het laatste type)
    [Predicate<T>]
    één parameter, een booleaans resultaat: [bool M(T p)]
    [Comparison<T>]
    twee parameters van hetzelfde type, een geheel getal als resultaat: [int M(T x, T y)]

    [Predicate<T>] en [Func<T, bool>] beschrijven dezelfde signatuur, maar zijn twee verschillende typen: [Predicate<T>] dateert uit .NET 2 en wordt gebruikt door de methoden van [List<T>] en [Array] ([FindAll], [RemoveAll], [Exists]…), terwijl LINQ, dat met .NET 3.5 is geïntroduceerd, [Func<T, bool>] gebruikt.

    • de methodenaam op regel 10 van de uitvoer is verrassend: de methoden op regels 39–50 zijn lokale functies van het hoofdprogramma (zie hoofdstuk 3). De compiler zet ze om in statische methoden van een door hem gegenereerde klasse, met een naam die geen enkel C#-programma kan schrijven.

    7.2. Delegatetypen definiëren

    Voorgedefinieerde typen volstaan vaak, maar u kunt ook uw eigen delegatetypen definiëren. De instructie:

    1
    public delegate int Operation(int n1, int n2);

    definieert een type met de naam [Operation], dat een methodemodel voorstelt met twee gehele getallen als parameters en een geheel getal als retourwaarde. In vergelijking met [Func<int, int, int>]heeft het type [Operation] een naam die het doel beschrijft, en hebben de parameters namen ([n1], [n2]) die ontwikkelhulpmiddelen tonen.

    Een variabele [op] van het type [Operation] wordt gebruikt om een lijst met methoden op te slaan die overeenkomen met het model [Operation]: dit heet een multicast-delegate.

    • Een methode van het type [f] wordt in de variabele [op] opgeslagen met [op = new Operation(f)] of, eenvoudiger, [op = f];
    • Om een methode [g] toe te voegen aan de lijst met reeds geregistreerde methoden, schrijft u [op += g];
    • Om een reeds geregistreerde methode [h] te verwijderen, schrijft u [op -= h];
    • De instructie [n = op(n1, n2)] voert alle in [op] geregistreerde methoden uit, in de volgorde waarin ze zijn geregistreerd, met de parameters [n1] en [n2]. Het geretourneerde resultaat [n] is dat van de laatst uitgevoerde methode.

    In de cursus van 2008 stond dat het niet mogelijk is de resultaten van alle methoden te verkrijgen. Het kan wel, maar niet met één aanroep: u moet de lijst met methoden doorlopen die door [GetInvocationList] wordt teruggegeven en ze een voor een aanroepen. In de praktijk geven methoden die in een multicast-delegate zijn geregistreerd meestal [void] terug.

// we definiëren een object van het type Operation om er methoden in te registreren
// we registreren de statische methode Increase
Operation op = Calculations.Increase;
// we voeren de delegate uit
int n = op(4, 7);
Console.WriteLine($"n={n}");

// aanmaken van een object c1 van het type Calculations
var c1 = new Calculations();
// we registreren de methode Add van c1 in de delegate
op = c1.Add;
// uitvoering van het delegate-object
n = op(2, 3);
Console.WriteLine($"n={n}");
// we registreren de methode Subtract van c1 in de delegate
op = c1.Subtract;
n = op(2, 3);
Console.WriteLine($"n={n}");

// registratie van twee methoden in de delegate (multicast delegate)
op = c1.Add;
op += c1.Subtract;
// uitvoering van het delegate-object: we krijgen het resultaat van de laatste methode
n = op(10, 4);
Console.WriteLine($"n={n}");
// de resultaten van alle methoden met de aanroeplijst
foreach (Operation method in op.GetInvocationList().Cast<Operation>())
{
    Console.WriteLine($"{method.Method.Name} -> {method(10, 4)}");
}
// we verwijderen een methode uit de delegate: het resultaat kan null zijn (type Operation?)
Operation? rest = op - c1.Subtract;
// we voeren de delegate uit als ze niet null is
if (rest is not null)
{
    n = rest(1, 1);
    Console.WriteLine($"n={n}");
}
// we verwijderen de laatste methode: de delegate wordt null
Operation? empty = rest - c1.Add;
Console.WriteLine($"empty is null: {empty is null}");
// ?.Invoke voert de delegate alleen uit als ze niet null is
Console.WriteLine($"empty?.Invoke(1, 1)={empty?.Invoke(1, 1)}");

    • regel 73: definitie van het delegatetype [Operation]. In een applicatie met instructies op hoog niveau (top-level statements) worden typedeclaraties (klassen, interfaces, delegates enzovoort) na de instructies van het hoofdprogramma geplaatst;
    • regels 48–67: de klasse [Calculations] heeft twee instantiemethoden, [Add] en [Subtract], en één statische methode, [Increase], die alle drie de signatuur van het type [Operation] hebben;
    • regel 5: de variabele [op] is van het type [Operation]. Daaraan wordt een eerste methodeverwijzing toegekend, die van de statische methode [Calculations.Increase];
    • regel 7: de delegate [op] wordt uitgevoerd. Alle methoden waarnaar [op] verwijst, worden uitgevoerd, met de parameters die aan [op] zijn doorgegeven. Hier wordt alleen de methode [Calculations.Increase] uitgevoerd;
    • regel 11: er wordt een instantie [c1] van de klasse [Calculations] aangemaakt;
    • regel 13: de instantiemethode [c1.Add] wordt aan de delegate [op] toegekend. [Increase] was een statische methode, [Add] is een instantiemethode: dat maakt niet uit. In het tweede geval slaat de delegate ook het object [c1] (de eigenschap [Target]) op waarop de methode wordt aangeroepen;
    • regel 18: doe hetzelfde voor de instantiemethode [Subtract];
    • regels 23–24: we registreren de twee methoden [Add] en [Subtract] in de delegate [op];
    • regel 26: beide methoden worden uitgevoerd (regels 8–9 van de resultaten). Het verkregen resultaat, 6, is dat van [Subtract], de laatst uitgevoerde methode;
    • regels 29–31: [GetInvocationList] geeft de lijst met methoden van de delegate terug als een array [Delegate[]]. De LINQ-methode [Cast<Operation>()] zet elk element ervan om naar [Operation], waardoor ze een voor een kunnen worden aangeroepen en elk resultaat kan worden opgehaald;
    • regel 34: de methode [Subtract] wordt uit de delegate verwijderd. De notatie ***[op -= c1.Subtract] is gelijkwaardig aan ***[op = op - c1.Subtract]***. Het resultaat van de operator [-] is van het type [Operation?]: als we de laatste methode uit een delegate verwijderen, krijgen we [null]* en geen lege delegate. De compiler, die nullable typen bijhoudt (zie hoofdstuk 3), zou waarschuwingen geven als u [op -= c1.Subtract] zou schrijven, gevolgd door [op(1, 1)]: [CS8601] bij het toekennen van een mogelijk null-waarde aan de niet-nullable variabele [op], en [CS8602] bij het aanroepen van de methode. We slaan het resultaat daarom op in een variabele van het type [Operation?] en controleren deze voordat we haar uitvoeren (regel 36);
    • regel 42: we verwijderen de laatste methode; de resulterende delegate is [null] (regel 17 van de resultaten);
    • regel 45: een delegate kan ook worden uitgevoerd via haar methode [Invoke]: [op(1, 1)] en [op.Invoke(1, 1)] zijn gelijkwaardig. Met de operator [?.] (C# 6) voert [empty?.Invoke(1, 1)] de delegate alleen uit als deze niet [null] is; anders evalueert de expressie naar [null] en wordt er niets uitgevoerd. Stringinterpolatie geeft [null] weer als een lege tekenreeks. Deze syntaxis zien we terug bij de bespreking van gebeurtenissen.

    Een delegate is een onveranderlijk object: de bewerkingen [+] en [-] (en dus [+=] en [-=]) wijzigen de bestaande delegate niet; ze maken een nieuwe aan. Deze eigenschap wordt belangrijk bij het behandelen van gebeurtenissen.

// 1 - een anonieme methode (C# 2): de body van de methode wordt ter plaatse geschreven
Func<int, int, int> add = delegate (int n1, int n2)
{
    return n1 + n2;
};
Console.WriteLine($"anonymous method: add(2, 3)={add(2, 3)}");

// 2 - hetzelfde met een lambda-expressie (C# 3): parameters => body
Func<int, int, int> subtract = (int n1, int n2) =>
{
    return n1 - n2;
};
Console.WriteLine($"block-bodied lambda: subtract(2, 3)={subtract(2, 3)}");

// 3 - de parametertypen worden afgeleid uit het doeltype van de delegate
Func<int, int, int> multiply = (n1, n2) => n1 * n2;
Console.WriteLine($"expression-bodied lambda: multiply(2, 3)={multiply(2, 3)}");

// 4 - één enkele parameter: de haakjes zijn optioneel
Func<int, int> square = x => x * x;
Predicate<string> isEmpty = s => s.Length == 0;
Console.WriteLine($"square(7)={square(7)}, isEmpty(\"\")={isEmpty("")}");

// 5 - geen parameter: lege haakjes
Func<string> greet = () => "Hello";
Action beep = () => Console.WriteLine("beep!");
Console.WriteLine(greet());
beep();

// 6 - een blokbody met meerdere instructies
Action<string, int> repeat = (text, times) =>
{
    for (int i = 0; i < times; i++)
    {
        Console.Write(text);
    }
    Console.WriteLine();
};
repeat("ab", 3);

// 7 - genegeerde parameters (discards): we hebben hun waarden niet nodig
EventHandler handler = (_, _) => Console.WriteLine("event received");
handler(null, EventArgs.Empty);

// 8 - een lambda die rechtstreeks als parameter van een methode wordt doorgegeven
List<int> numbers = [3, 8, 1, 6, 5, 4];
Console.WriteLine($"even: {string.Join(" ", numbers.FindAll(n => n % 2 == 0))}");
numbers.Sort((n1, n2) => n2.CompareTo(n1));
Console.WriteLine($"descending order: {string.Join(" ", numbers)}");

    Opmerkingen:

    • regels 4–6: een anonieme methode. Het sleutelwoord [delegate] wordt gevolgd door de parameterlijst en de methodetekst. De compiler genereert een methode (met een zelfgekozen naam) en maakt een delegate [Func<int, int, int>] aan die ernaar verwijst. Er is geen methodenaam of retourtype: het retourtype wordt afgeleid uit de instructies [return];
    • regels 11–13: hetzelfde met een lambda-expressie. We schrijven de parameterlijst, de operator [=>] (die wordt gelezen als „geeft” of „zodanig dat”) en vervolgens de body. Een lambda waarvan de body een blok tussen accolades is, heet een lambda met blokbody (statement lambda);
    • regel 18: de parametertypen ontbreken. De compiler leidt ze af uit het doeldelegatetype [Func<int, int, int>]: [n1] en [n2] zijn van het type [int]. De body is teruggebracht tot een expressie, waarvan de waarde het resultaat van de lambda is: dit is een lambda met een expressiebody (lambda-expressie). Dit is de meest voorkomende vorm;
    • regel 22: bij één parameter waarvan het type niet is opgegeven, zijn haakjes optioneel. [x => x * x] wordt gelezen als „x geeft x maal x”. Regel 23: dezelfde lambda met één parameter, van het type [string], geeft een booleaanse waarde terug: het is een [Predicate<string>];
    • regels 27–28: zonder parameters worden lege haakjes gebruikt. Een lambda waarvan de body een methodeaanroep is ([void]) is geschikt voor een delegate ([Action]);
    • regels 33–39: een lambda met een blokbody kan alle soorten instructies bevatten: declaraties, lussen, tests enzovoort;
    • regel 44: het onderstrepingsteken [_] geeft een genegeerde parameter aan (discard, C# 9). Het wordt gebruikt wanneer de signatuur van de delegate parameters vereist die de lambda niet nodig heeft, wat vaak voorkomt bij event handlers;
    • regel 49: het meest voorkomende gebruik van lambda's is ze rechtstreeks als parameter door te geven aan een methode die een delegate verwacht. Vergelijk met [delegates-01.cs]: het is niet meer nodig een methode [IsEven] te schrijven;
    • regel 50: een lambda van het type [Comparison<int>] die de gebruikelijke vergelijking omkeert: de lijst wordt aflopend gesorteerd.

    Laten we de vormen van een lambda-expressie op een rij zetten:

    Vorm
    Voorbeeld
    getypeerde parameters, blokbody
    [(int a, int b) => { return a + b; }]
    niet-getypeerde parameters, expressiebody

    één niet-getypeerde parameter

    geen parameters

    7.5. Gebeurtenissen afhandelen

    7.5.1. Het .NET-gebeurtenismodel

    Delegates worden gebruikt om gebeurtenissen te definiëren. Een klasse [C1] kan als volgt een gebeurtenis [Evt1] definiëren:

    • Een delegate-type wordt binnen of buiten de klasse [C1] gedefinieerd:
    1
    delegate void Evt(T1 param1, T2 param2, ...);
    • De klasse [C1] definieert een veld van dit delegate-type:
    1
    public Evt? Evt1;
    • Wanneer een instantie [c1] van de klasse [C1] een gebeurtenis wil signaleren, voert die zijn delegate [Evt1] uit en geeft daarbij de parameters door die door het type [Evt] zijn gedefinieerd. Alle methoden die in het delegate [Evt1] zijn geregistreerd, worden dan met deze parameters uitgevoerd. Men kan zeggen dat zij op de hoogte zijn gebracht van de gebeurtenis [Evt1];
    • als een object [c2] dat het object [c1] gebruikt, op de hoogte wil worden gebracht van de gebeurtenis [Evt1] van het object [c1], registreert het een van zijn methoden, [c2.M], bij het delegate [c1.Evt1]. Zijn methode [c2.M] wordt dan telkens uitgevoerd wanneer de gebeurtenis [Evt1] zich voordoet bij het object [c1]. Het object kan zich ook afmelden wanneer het niet langer op de hoogte gebracht wil worden;
    • omdat het delegate [c1.Evt1] meerdere methoden kan registreren, kunnen verschillende objecten [ci] zich bij [c1.Evt1] registreren om van de gebeurtenis op de hoogte te worden gebracht.

    In dit scenario hebben we:

    • een klasse die een gebeurtenis signaleert (ook wel „publiceert" of „uitzendt");
    • klassen die van deze gebeurtenis op de hoogte worden gebracht. Zij zijn geabonneerd op de gebeurtenis;
    • een delegate-type dat de signatuur definieert van de methoden die van de gebeurtenis op de hoogte worden gebracht. Deze methoden heten gebeurtenis-handlers.

    Dit is het ontwerppatroon Observer: de zender kent zijn abonnees niet; hij brengt hen alleen op de hoogte.

    Het .NET-framework definieert een standaardsignatuur voor een gebeurtenis-delegate:

    1
    public delegate void MyEventHandler(object? sender, EventArgs e);
    • [sender]: het object dat de gebeurtenis heeft veroorzaakt;
    • [e]: een object van het type [EventArgs] of van een afgeleid type, dat informatie over de gebeurtenis levert;
    • Volgens afspraak eindigt de naam van het delegate-type op [EventHandler].

    Het definieert ook een standaardmanier om in een klasse een gebeurtenis van het type [MyEventHandler] te declareren:

    1

3
4
5
    public class C1
{
    public event MyEventHandler? Evt1;
    ...
}

    Het veld [Evt1] is van het delegate-type. Het sleutelwoord [event] beperkt de bewerkingen die erop kunnen worden uitgevoerd:

    • Van buiten de klasse [C1] zijn alleen de bewerkingen [+=] en [-=] toegestaan. Zo wordt voorkomen dat andere objecten de geabonneerde methoden overschrijven of verwijderen (bijvoorbeeld per ongeluk door [=] te schrijven in plaats van [+=]). U kunt zich alleen abonneren ([+=]) of afmelden ([-=]);
    • alleen de klasse [C1] kan het delegate uitvoeren, dat wil zeggen de gebeurtenis activeren: [Evt1?.Invoke(this, e)].

    Als u van buiten de klasse [c1.Evt1 = null;] of [c1.Evt1(null, EventArgs.Empty);] probeert te schrijven, reageert de compiler met: [error CS0070: The event 'C1.Evt1' can only appear on the left hand side of += or -= (except when used from within the type 'C1')].

    In plaats van voor elke gebeurtenis een delegate-type te definiëren, gebruiken we het voorgedefinieerde generieke delegate:

    1
    public delegate void EventHandler<TEventArgs>(object? sender, TEventArgs e);

    Het type [TEventArgs] is dat van de tweede parameter, het object dat de gebeurtenis beschrijft. Met dit generieke delegate volgt de declaratie van een gebeurtenis [X] in een klasse [C] het onderstaande aanbevolen patroon:

    • definieer een type [XEventArgs] afgeleid van [EventArgs] om informatie over de gebeurtenis [X] te bundelen;
    • definieer een gebeurtenis van het type [EventHandler<XEventArgs>] in de klasse [C];
    • definieer in de klasse [C] een beschermde en virtuele methode [protected virtual void OnX(XEventArgs e)] die bedoeld is om de gebeurtenis [X] aan de abonnees te publiceren. De methode is virtueel zodat een afgeleide klasse kan wijzigen hoe de gebeurtenis wordt gepubliceerd.

    In 2008 moest het type [TEventArgs] van [EventArgs] zijn afgeleid (beperking [where TEventArgs : EventArgs]). Deze beperking is in .NET Framework 4.5 vervallen: elk type is toegestaan, ook een [record]. Volgens afspraak blijft men echter afleiden van [EventArgs]. Merk op dat een [record] niet kan worden afgeleid van [EventArgs]: een [record] kan alleen van een ander [record] erven (fout: [CS8864: Records may only inherit from object or another record]). We gebruiken daarom een gewone klasse.

public static class Tools
{
    // filtert een reeks met een predicaat: het equivalent van Where
    public static IEnumerable<T> Filter<T>(IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (T element in source)
        {
            if (predicate(element))
            {
                // het element wordt teruggegeven aan de aanroeper; de iteratie gaat hier verder
                yield return element;
            }
        }
    }
}

public static class Extensions
{
    // extension members (C# 14) van IEnumerable<T>
    extension<T>(IEnumerable<T> source)
    {

        public IEnumerable<T> Filter(Func<T, bool> predicate) => Tools.Filter(source, predicate);

        // transformeert elk element: het equivalent van Select
        public IEnumerable<TResult> Transform<TResult>(Func<T, TResult> transformation)
        {
            foreach (T element in source)
            {
                yield return transformation(element);
            }
        }
    }

    • regels 5-6: dezelfde lambda wordt toegewezen aan een delegate [Func<int, bool>] en daarna aan een expressieboom [Expression<Func<int, bool>>];
    • regel 9: een delegate kan alleen zijn type tonen; de code is gecompileerd en onleesbaar;
    • regel 11: een expressieboom kan daarentegen wel worden getoond. Het resultaat (regel 3) geeft de lambda weer: [AndAlso] is de naam van de operator [&&];
    • regel 12: we kunnen de boom bevragen: zijn parameters, het type van zijn resultaat en zijn body ([Body]);
    • regels 21-39: een recursieve methode die de boom toont. Elk knooppunt is een object dat is afgeleid van de klasse [Expression]: [BinaryExpression] voor een bewerking met twee operanden ([&&], [>], [==], [%]), [ParameterExpression] voor een parameter, [ConstantExpression] voor een constante. [switch], met patroonfiltering op basis van het type, handelt elk geval af. De resultaten (regels 6-14) tonen de structuur van de expressie [n > 5 && n % 2 == 0];
    • regel 17: een expressieboom kan tijdens de uitvoering worden gecompileerd tot een delegate en vervolgens worden uitgevoerd.

    Wat is hiervan het nut? Een delegate kan alleen binnen het programma worden uitgevoerd. Een expressieboom kan worden geanalyseerd en vertaald naar een andere taal. Dat is wat Entity Framework Core doet, en daar gaan we in hoofdstuk 11 verder op in. Wanneer u een LINQ-query schrijft op een databasetabel, bijvoorbeeld [context.Brackets.Where(t => t.Limit > 20000)], is de gebruikte methode [Where] niet die van [IEnumerable<T>] maar die van [IQueryable<T>], waarvan de parameter een [Expression<Func<T, bool>>] is. EF Core doorloopt deze boom, net als onze methode [Display], en vertaalt hem naar een SQL-clausule [WHERE limits > 20000] die door de databaseserver wordt uitgevoerd. Dezelfde lambda, op dezelfde manier geschreven, wordt dus .NET-code of SQL-code, afhankelijk van het type van de parameter die ze ontvangt.

    7.8. Conclusie

    Belangrijkste punten van dit hoofdstuk:

    • Een delegate is een object dat verwijst naar een of meer methoden met een bepaalde signatuur. De voorgedefinieerde typen [Func<>], [Action<>]en [Predicate<T>] maken het meestal overbodig om eigen delegate-typen te definiëren;
    • met lambda-expressies schrijft u de methode precies op de plaats waar u het delegate aanmaakt. Ze leggen de omringende variabelen vast (let op bij [for]-lussen);
    • een delegate kan een interface met één methode vervangen en biedt meer flexibiliteit;
    • een gebeurtenis is een delegate dat wordt beschermd door het sleutelwoord [event]: u abonneert zich met [+=], meldt zich af met [-=], en alleen de klasse die de gebeurtenis declareert, activeert hem met [Evt?.Invoke(this, e)];
    • LINQ is gebouwd op methoden die delegates accepteren, en EF Core op expressiebomen.

    Delegates komen in de volgende hoofdstukken opnieuw aan bod: een taak ([Task.Run]) voert een delegate uit in een andere thread (hoofdstukken 8 en 9), en de ASP.NET Core-webservices koppelen lambda's aan HTTP-adressen (hoofdstuk 13).
