    8. Threads

    Dit hoofdstuk introduceert het gelijktijdig uitvoeren van meerdere stukken code binnen één programma: threads (uitvoeringsthreads) en de hulpmiddelen om ze te synchroniseren. In 2008 hadden de meeste machines maar één processor en was parallellisme grotendeels een illusie die door het besturingssysteem in stand werd gehouden. Tegenwoordig heeft zelfs de eenvoudigste laptop meerdere kernen: meerdere threads draaien daadwerkelijk tegelijkertijd, waardoor de hier besproken synchronisatieproblemen nog vaker voorkomen.

    De voorbeelden zijn single-file-applicaties ([dotnet run threads-01.cs]) in de map [08-threads]. Merk op dat de impliciete directives [using] voor deze applicaties [System.Threading] en [System.Threading.Tasks] omvatten: de klassen [Thread], [Lock], [Mutex], [Monitor], [Interlocked], [Task]… kunnen worden gebruikt zonder de directive [using].

    Een waarschuwing vooraf: de resultaten van een multithreaded programma verschillen van de ene uitvoering tot de andere. De volgorde waarin threads de processor krijgen toegewezen, hangt af van het besturingssysteem, het aantal processors en de belasting van de machine. De resultaten in dit hoofdstuk zijn verkregen op een Linux-machine met twee processors die met andere programma's werd gedeeld. Als u de voorbeelden uitvoert, krijgt u vergelijkbare resultaten, maar ze zullen zelden identiek zijn.

    8.1. De klasse Thread

    Wanneer een applicatie wordt gestart, draait ze in een uitvoeringsstroom die thread heet. De .NET-klasse die een thread modelleert, is de klasse [System.Threading.Thread]. De belangrijkste constructors, eigenschappen en methoden zijn de volgende:

    8.2. Threads aanmaken

    Het is mogelijk om applicaties te hebben waarin stukken code „gelijktijdig" in verschillende threads worden uitgevoerd. Als de machine minder processors heeft dan er threads klaarstaan om te worden uitgevoerd, delen de threads de processors: elke thread gebruikt beurtelings een processor gedurende korte tijd (enkele milliseconden). Op een machine met meerdere processors worden meerdere threads daadwerkelijk tegelijkertijd uitgevoerd. De tijd die aan een thread wordt toegekend, hangt van verschillende factoren af, waaronder zijn prioriteit, die een standaardwaarde heeft maar programmatisch kan worden ingesteld (eigenschap [Priority]). Een thread die de processor heeft, kan die voortijdig vrijgeven:

    • door op een gebeurtenis te wachten (voltooiing van een andere thread met [Join], wachten op een signaal);
    • door gedurende een opgegeven tijd in slaap te gaan ([Sleep]).

    Een thread T wordt eerst aangemaakt met een van de hierboven gepresenteerde constructors, bijvoorbeeld:

    1
    Thread t = new Thread(Display);

    waarbij [Display] een methode is met een van de volgende twee signaturen:

    1
2
    void Display();
void Display(object? obj);

    Het aanmaken van een thread start hem niet:

    • de uitvoering van thread T wordt gestart met [T.Start()]: de methode die aan de constructor van T is doorgegeven, wordt dan door thread T uitgevoerd. De code die de instructie [T.Start()] uitvoert, wacht niet tot thread T klaar is, maar gaat meteen door met de volgende instructie. We hebben dan twee parallel draaiende threads. Ze moeten vaak met elkaar communiceren om de voortgang van het gedeelde werk te volgen: dit is het probleem van de synchronisatie van threads;
    • Eenmaal gestart draait thread T zelfstandig. Hij stopt wanneer de methode die hij uitvoert is afgerond;
    • we kunnen wachten tot hij klaar is met [T.Join()]. Dit is een blokkerende instructie: de thread die haar uitvoert, wordt geblokkeerd totdat thread T zijn werk heeft afgerond. Dit is een elementaire synchronisatiemethode.

    // wachten op het einde van een thread met Join - threads aangemaakt met een lambda

// we geven de hoofdthread een naam
Thread.CurrentThread.Name = "Main";

// aanmaken van 5 threads
var tasks = new Thread[5];
for (int i = 0; i < tasks.Length; i++)
{
    // lokale kopie van i, vastgelegd door de lambda
    int number = i;
    // de thread voert de lambda uit, die Display aanroept met een getypeerde parameter
    tasks[i] = new Thread(() => Display(number, 1000 + 100 * number)) { Name = i.ToString() };
    tasks[i].Start();
}

// we wachten op het einde van alle threads
foreach (Thread task in tasks)
{
    // de hoofdthread is geblokkeerd tot het einde van de thread [task]
    task.Join();
}
// einde van de hoofdthread
Console.WriteLine($"End of thread {Thread.CurrentThread.Name} at {DateTime.Now:HH:mm:ss.fff}");

{
    Console.WriteLine($"Start of execution of task {number} in thread {Thread.CurrentThread.Name}: {DateTime.Now:HH:mm:ss.fff}");
    // slapen gedurende [duration] milliseconden
    Thread.Sleep(duration);
    Console.WriteLine($"End of execution of task {number} in thread {Thread.CurrentThread.Name}: {DateTime.Now:HH:mm:ss.fff}");
}

    • regel 11: de lambda gebruikt een kopie van de lusvariabele [i]. Dit is essentieel: een lambda legt de variabele vast, niet de waarde ervan. In een [for]-lus is de variabele [i] voor alle iteraties dezelfde; als de lambda [i] zou gebruiken, kon een thread die laat start de waarde van [i] van een latere iteratie lezen, of zelfs de eindwaarde 5. De variabele [number], die in de lusbody is gedeclareerd, is daarentegen voor elke iteratie een nieuwe variabele (ook een [foreach]-lusvariabele is vanaf C# 5 voor elke iteratie nieuw);
    • regels 18-21: de hoofdthread wacht op elk van de threads. Hij wordt eerst geblokkeerd in afwachting van thread 0, dan van thread 1, enzovoort. Wanneer hij de lus verlaat, zijn de 5 threads die hij heeft gestart klaar;
    • regel 31: taak nr. i slaapt 1.000 + 100 × i milliseconden, zodat de threads in een bekende volgorde eindigen.

    8.3. De voordelen van threads

    Nu we hebben aangetoond dat er een standaardthread bestaat, de thread die het hoofdprogramma uitvoert, en we weten hoe we extra threads kunnen aanmaken, kijken we naar de voordelen van threads. Er zijn twee hoofdtoepassingen:

    • om alle processors van de machine te benutten voor een tijdrovende berekening: het werk wordt in delen verdeeld die aan verschillende threads worden toegewezen. Dat doen we aan het einde van dit hoofdstuk met de bibliotheek [Parallel];
    • om meerdere taken tegelijk uit te voeren, vooral wanneer sommige daarvan voornamelijk uit wachten bestaan (op een netwerkantwoord, een schijfleesbewerking of gebruikersinvoer). Dit is het geval bij client-server-internetapplicaties, die we in een later hoofdstuk behandelen.

    In een client-server-internetapplicatie beantwoordt een server op een machine met de naam S1 verzoeken van clients op externe machines C1, C2, ..., Cn:

    We gebruiken dagelijks internettoepassingen die dit patroon volgen: webservices, e-mail, bestandsoverdracht enzovoort. In het bovenstaande diagram moet de server S1 de clients Ci gelijktijdig bedienen. Als we het voorbeeld van een bestandsserver nemen, weten we dat een overdracht soms enkele minuten kan duren. Het is uitgesloten dat één client de server zo lang monopoliseert. Een gebruikelijke oplossing is dat de server evenveel threads aanmaakt als er clients zijn. Elke thread is dan verantwoordelijk voor de afhandeling van één bepaalde client:

    In de praktijk gebruikt de server een threadpool met een beperkt aantal threads, zoals verderop beschreven. Moderne servers gaan nog een stap verder: terwijl een client op een antwoord van het netwerk wacht, wordt er geen thread voor gereserveerd. Dat is mogelijk dankzij asynchroon programmeren, het onderwerp van het volgende hoofdstuk.

    8.5. Gelijktijdige toegang tot gedeelde bronnen

    8.5.1. Ongesynchroniseerde gelijktijdige toegang

    8.5.3. De klasse Mutex

    De klasse [System.Threading.Mutex] maakt het eveneens mogelijk kritieke secties te begrenzen. Ze verschilt van de clausule [lock] wat betreft zichtbaarheid:

    • de clausule [lock] synchroniseert threads binnen dezelfde applicatie;
    • de klasse [Mutex] kan threads van verschillende applicaties (of processen) synchroniseren als ze een naam krijgt.

    Een [Mutex] is een object van het besturingssysteem: het gebruik ervan is veel kostbaarder qua middelen dan dat van een [lock]. Voor threads binnen hetzelfde proces gebruiken we daarom bij voorkeur [lock]; [Mutex] wordt vooral tussen processen gebruikt. We gebruiken de volgende constructors en methoden:

    [bool WaitOne()]

    8.5.4. De klasse AutoResetEvent

    1

    1

    8.5.6. De klasse Interlocked

    De klasse [Interlocked] maakt eenvoudige bewerkingen op een variabele atomair: de bewerking wordt volledig door de thread uitgevoerd, zonder dat een andere thread de variabele halverwege de bewerking kan waarnemen of wijzigen.     8.6. Gelijktijdige toegang tot meerdere gedeelde bronnen

    8.6.1. Deadlock

    In onze voorgaande voorbeelden werd één enkele bron door de verschillende threads gedeeld. De situatie wordt ingewikkelder als er meerdere bronnen zijn die van elkaar afhankelijk zijn. Er kan met name een deadlock optreden: twee threads wachten op elkaar. Bekijk de volgende acties, die achtereenvolgens plaatsvinden:

    • een thread T1 verkrijgt het slot V1 om toegang te krijgen tot een gedeelde bron R1;
    • een thread T2 verkrijgt het slot V2 om toegang te krijgen tot een gedeelde bron R2;
    • thread T1 vraagt slot V2 aan. Hij wordt geblokkeerd;
    • thread T2 vraagt slot V1 aan. Hij wordt geblokkeerd.

    De threads T1 en T2 wachten voor onbepaalde tijd op elkaar. Er zijn verschillende oplossingen mogelijk:

    • vraag beide bronnen tegelijk aan met één enkel slot. Dat is niet altijd mogelijk als het leidt tot een langdurige vergrendeling van een kostbare bron;
    • verkrijg altijd sloten in dezelfde volgorde: als alle threads V1 vóór V2 verkrijgen, is een deadlock onmogelijk. Dit is de meestgebruikte regel;
    • een thread die V1 vasthoudt en V2 niet kan verkrijgen, geeft V1 vrij om een deadlock te voorkomen.

// neemt de 1e resource en probeert daarna gedurende [timeout] de 2e te nemen
static void Work(Lock first, string firstName, Lock second, string secondName, TimeSpan timeout)
{
    string name = Thread.CurrentThread.Name ?? "?";
    lock (first)
    {
        Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} obtained {firstName}");
        // we geven de andere thread de tijd om zijn eerste resource te nemen
        Thread.Sleep(500);
        Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} requests {secondName}");
        // aanvraag met een maximale wachttijd, in plaats van een lock die onbeperkt zou wachten
        if (second.TryEnter(timeout))
        {
            try
            {
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} obtained {secondName} and works with {firstName} and {secondName}");
            }
            finally
            {
                second.Exit();
            }
        }
        else
        {
            Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} did not obtain {secondName} within {timeout.TotalSeconds} s: it releases {firstName} and gives up");
        }
    }
}

    8.6.2. Een voorbeeld: lezers en schrijvers

    Bekijk het volgende voorbeeld:

    • we hebben een array waarin sommige threads gegevens schrijven (de schrijvers) en andere ze lezen (de lezers);
    • de schrijvers zijn gelijkwaardig maar exclusief: slechts één schrijver tegelijk kan gegevens in de array plaatsen;
    • de lezers zijn gelijkwaardig maar exclusief: slechts één lezer tegelijk kan de in de array opgeslagen gegevens lezen;
    • een lezer kan alleen gegevens uit de array lezen wanneer een schrijver er gegevens in heeft geplaatst, en een schrijver kan alleen nieuwe gegevens in de array plaatsen wanneer de reeds aanwezige gegevens door een lezer zijn gelezen.

    Er zijn twee soorten gedeelde bronnen:

    • de array waarin wordt geschreven: slechts één schrijver tegelijk heeft er toegang toe;
    • de array waaruit wordt gelezen: slechts één lezer tegelijk heeft er toegang toe.

    en een volgorde voor het gebruik van deze bronnen:

    • een lezer moet altijd op een schrijver volgen;
    • een schrijver moet altijd op een lezer volgen, behalve de eerste keer.

    De toegang tot deze twee bronnen kan worden beheerd met twee slagbomen van het type [AutoResetEvent]:

    • de slagboom [canWrite] beheert de toegang van de schrijvers tot de array;
    • de slagboom [canRead] beheert de toegang van de lezers tot de array;
    • de slagboom [canWrite] wordt open aangemaakt, zodat de eerste schrijver erdoor kan en alle andere worden geblokkeerd;
    • De barrière [canRead] wordt gemaakt in de gesloten toestand, zodat alle lezers worden geblokkeerd;
    • wanneer een schrijver zijn werk heeft afgerond, opent hij barrière [canRead] om een lezer binnen te laten;
    • wanneer een lezer zijn werk heeft afgerond, opent hij de barrière [canWrite] om een schrijver binnen te laten.

    private static readonly int[] data = new int[3];
    // geeft aan dat de inhoud van data kan worden gelezen: aan het begin gesloten
    private static readonly AutoResetEvent canRead = new(false);
    // geeft aan dat data kan worden geschreven: aan het begin open
    private static readonly AutoResetEvent canWrite = new(true);

    // de inhoud van de array lezen
    public static void Read()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Read] started by thread {name}");
        // we wachten op toestemming om te lezen
        canRead.WaitOne();
        // lezen van de array
        for (int i = 0; i < data.Length; i++)
        {
            // 0,5 s wachten: de thread verliest de processor
            Thread.Sleep(500);
            Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: reader {name} read the number {data[i]}");
        }
        // we staan een schrijver toe
        canWrite.Set();
        Console.WriteLine($"Method [Read] finished by thread {name}");
    }

    // in de array schrijven
    public static void Write()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Write] started by thread {name}");
        // we wachten op toestemming om te schrijven
        canWrite.WaitOne();
        // schrijven van de array

        {
            // 0,5 s wachten

        canRead.Set();
        Console.WriteLine($"Method [Write] finished by thread {name}");
    }
}

    8.6.3. De klasse Monitor

    In het vorige voorbeeld wordt, wanneer de schrijvers geblokkeerd zijn op de instructie [canWrite.WaitOne()], één van hen – willekeurig welke – gedeblokkeerd door de bewerking [canWrite.Set()]. Als u de barrière voor een bepaalde schrijver wilt openen, wordt het ingewikkelder.

    Neem als analogie een overheidsloket met meerdere balies. Wanneer een klant binnenkomt, pakt hij een nummer uit de nummerautomaat en gaat zitten. De klanten worden via een omroepinstallatie op nummer opgeroepen. Tijdens het wachten kan de klant doen wat hij wil: lezen of indommelen. Telkens wanneer de omroepinstallatie een nummer afroept, wordt hij gewekt. Is het zijn nummer, dan staat de klant op en gaat naar de balie; zo niet, dan gaat hij verder met waar hij mee bezig was. Met threads kunnen we op vergelijkbare wijze te werk gaan. Laten we het voorbeeld van de schrijvers nemen:

    Bij threads

    het loket komt vrij en het nummer van de volgende schrijver wordt afgeroepen
    de thread die uit de array las, meldt de schrijvers dat de array beschikbaar is. Die thread of een andere thread heeft bepaald welke schrijver verder mag

// de gedeelde resource en haar synchronisatie
static class Board
{
    // de array die tussen lezers en schrijvers wordt gedeeld
    private static readonly int[] data = new int[3];
    // de toegangstokens van de lees- en schrijftellers
    private static readonly object canRead = new();
    private static readonly object canWrite = new();
    // de toegangsvoorwaarden van de tellers
    private static bool readingAllowed = false;
    private static bool writingAllowed = false;
    private static int nextReader = 0;
    private static int nextWriter = 0;
    // de volgorde van de lezers en van de schrijvers
    public static string[] ReadOrder { get; set; } = [];
    public static string[] WriteOrder { get; set; } = [];

    // opent de schrijfteller
    public static void AllowWriting()
    {
        lock (canWrite)
        {
            writingAllowed = true;
            // we maken alle schrijvers wakker die op het token wachten
            Monitor.PulseAll(canWrite);
        }
    }

    // de inhoud van de array lezen
    public static void Read()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Read] started by thread {name}");
        // we vragen het token van de leesteller aan
        lock (canRead)
        {
            // zolang het niet onze beurt is, geven we het token terug en wachten we
            while (!readingAllowed || ReadOrder[nextReader] != name)
            {
                Monitor.Wait(canRead);
            }
            // bij de teller: lezen van de array
            for (int i = 0; i < data.Length; i++)
            {
                Thread.Sleep(500);
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: reader {name} read the number {data[i]}");
            }
            // volgende lezer
            readingAllowed = false;
            nextReader++;
            // we melden de schrijvers dat ze mogen schrijven
            lock (canWrite)
            {
                writingAllowed = true;
                Monitor.PulseAll(canWrite);
            }
            Console.WriteLine($"Method [Read] finished by thread {name}");
        }
    }

    // in de array schrijven
    public static void Write()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Write] started by thread {name}");
        // we vragen het token van de schrijfteller aan
        lock (canWrite)
        {
            // zolang het niet onze beurt is, geven we het token terug en wachten we
            while (!writingAllowed || WriteOrder[nextWriter] != name)
            {
                Monitor.Wait(canWrite);
            }
            // bij de teller: schrijven van de array
            for (int i = 0; i < data.Length; i++)
            {
                Thread.Sleep(500);
                data[i] = Random.Shared.Next(0, 1000);
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: writer {name} wrote the number {data[i]}");
            }
            // volgende schrijver
            writingAllowed = false;
            nextWriter++;
            // we melden de lezers dat ze mogen lezen
            lock (canRead)
            {
                readingAllowed = true;
                Monitor.PulseAll(canRead);
            }
            Console.WriteLine($"Method [Write] finished by thread {name}");
        }
    }
}

    8.7. Concurrente collecties

    De vorige voorbeelden beschermden zeer eenvoudige gedeelde gegevens (een teller, een array).     8.8. De threadpool

    Tot nu toe hebben we threads beheerd door ze aan te maken met [new Thread(...)] en ze vervolgens uit te voeren met [Start()]. Het aanmaken van een thread is een relatief kostbare bewerking: het systeem moet er onder meer een stack voor reserveren, en elke thread neemt geheugen in beslag zolang hij bestaat. In het hoofdstuk over databases zullen we zien dat er connectionpools bestaan: geopende verbindingen worden in reserve gehouden en uitgeleend aan threads die erom vragen, omdat het openen van een verbinding kostbaar is. Een vergelijkbaar systeem bestaat voor threads: de threadpool (ThreadPool) van .NET.

    • Zolang het aantal threads in de pool onder een minimumdrempel blijft, maakt de pool onmiddellijk een nieuwe thread aan voor elke taak die geen vrije thread vindt. Standaard is dit minimum gelijk aan het aantal processors; het kan worden uitgelezen met [ThreadPool.GetMinThreads(out min1, out min2)] en gewijzigd met [ThreadPool.SetMinThreads(min1, min2)]. De pool beheert twee soorten threads: worker-threads (min1), die de aan hen toegewezen taken uitvoeren, en asynchrone I/O-threads (min2);
    • als dit aantal onvoldoende is, maakt de pool stapsgewijs extra threads aan, tot een maximum dat kan worden uitgelezen met [ThreadPool.GetMaxThreads(out max1, out max2)] en gewijzigd met [ThreadPool.SetMaxThreads(max1, max2)].     • Een thread die een taak heeft voltooid, wordt niet vernietigd: hij keert terug naar de pool en wordt gebruikt voor de volgende taak.

    8.10. Gegevens die lokaal zijn voor een thread

    8.10.1. Het principe

    Neem een applicatie met drie lagen:

    Stel dat de applicatie meerdere gebruikers heeft, zoals een webapplicatie. Elk gebruikersverzoek wordt afgehandeld door een thread. De levenscyclus van de thread is als volgt:

    • de thread wordt aangemaakt of uit de threadpool gehaald om aan het verzoek van een gebruiker te voldoen;
    • als dit verzoek gegevens vereist, voert de thread een methode uit in de laag [ui], die een methode aanroept in de laag [business], die op haar beurt een methode aanroept in de laag [dao];
    • de thread geeft het antwoord terug aan de gebruiker. Daarna eindigt hij of keert hij terug naar de threadpool.

    Tijdens de tweede stap kan het nuttig zijn dat de thread over eigen gegevens beschikt, dat wil zeggen gegevens die niet met andere threads worden gedeeld. Deze gegevens kunnen bijvoorbeeld toebehoren aan de specifieke gebruiker die de thread bedient en in de verschillende lagen [ui, business, dao] worden gebruikt zonder dat ze aan elke methode als parameter worden doorgegeven.

    • het attribuut [[ThreadStatic]] op een statisch veld: elke thread heeft zijn eigen instantie van het veld;
    • de klasse [ThreadLocal<T>]: een object waarvan de eigenschap [Value] voor elke thread een andere waarde heeft. Een functie die aan de constructor wordt doorgegeven, levert de beginwaarde voor elke thread.

    threads[i] = new Thread(() =>
    {
        // schrijven
        Context.Shared = number;
        Context.PerThread = number;
        // thread T2 stelt geen gebruiker in: ze krijgt de standaardwaarde
        if (number != 2)
        {
            Context.User.Value = $"user{number}";

        // we laten de andere threads op hun beurt schrijven
        Thread.Sleep(200);
        // opnieuw lezen

    • in de laag [dao] alleen de basisbewerkingen opnemen (een artikel invoegen, wijzigen, verwijderen en lezen);
    • bewerkingen die meerdere artikelen tegelijk bijwerken, verplaatsen naar de laag [business]. Deze bewerkingen gebruiken de basisbewerkingen van de laag [dao].

    Het voordeel van deze oplossing is dat dezelfde laag [dao] ongewijzigd kan worden gebruikt met verschillende [business]-lagen. Zij brengt een uitdaging met zich mee bij het beheer van de transactie die de atomair uit te voeren updates groepeert:

    • de transactie moet door de laag [business] worden gestart voordat deze de methoden van de laag [dao] aanroept;
    • de methoden in de laag [dao] moeten op de hoogte zijn van het bestaan van de transactie om eraan te kunnen deelnemen;
    • de transactie moet door de laag [business] worden afgerond (commit of rollback).

    Om ervoor te zorgen dat de methoden van de laag [dao] op de hoogte zijn van een lopende transactie, zou de transactie als parameter aan elke methode van de laag [dao] kunnen worden toegevoegd. Die parameter zou dan voorkomen in de signatuur van de methoden van de interface, waardoor de interface aan een specifieke gegevensbron zou worden gekoppeld. Threadlokale gegevens bieden een elegantere oplossing: de laag [business] plaatst de transactie in de threadlokale gegevens, en daar haalt de laag [dao] haar op. De methodesignaturen van de laag [dao] hoeven niet te worden gewijzigd. Meerdere threads (meerdere gebruikers) kunnen tegelijk werken: elk heeft zijn eigen transactie.

// een gesimuleerde transactie: ze legt vast hoe elke update ongedaan wordt gemaakt
class Transaction
{
    private static int counter;
    private readonly Stack<Action> undos = new();
    public int Number { get; } = Interlocked.Increment(ref counter);

    // legt de bewerking vast die een update ongedaan maakt
    public void Log(Action undo) => undos.Push(undo);
    // bevestigt de transactie: de updates blijven behouden
    public void Commit() => undos.Clear();
    // draait de transactie terug: de updates worden ongedaan gemaakt, van de laatste naar de eerste
    public void Rollback()
    {
        while (undos.TryPop(out Action? undo))
        {
            undo();
        }
    }
}

    private readonly List<Article> table = [];
    private readonly Lock padlock = new();
    private int nextId = 1;

    public int InsertArticle(Article article)
    {
        // loopt er een transactie in de huidige thread?
        Transaction? transaction = ThreadContext.Transaction.Value;
        lock (padlock)
        {
            if (table.Any(a => a.Name == article.Name))
            {
                throw new InvalidOperationException($"an article named [{article.Name}] already exists");
            }
            Article inserted = article with { Id = nextId++ };
            table.Add(inserted);
            // binnen een transactie leggen we vast hoe de invoeging ongedaan kan worden gemaakt
            transaction?.Log(() =>
            {
                lock (padlock)
                {
                    table.Remove(inserted);
                }
            });
            string mode = transaction is null ? "outside a transaction" : $"in transaction {transaction.Number}";
            Console.WriteLine($"[{Thread.CurrentThread.Name}] [dao] insertion of {inserted.Name} (id {inserted.Id}) {mode}");
            return 1;
        }
    }

    public List<Article> GetAllArticles()
    {
        lock (padlock)
        {
            return [.. table];
        }
    }

    public void DeleteAllArticles()
    {
        lock (padlock)
        {
            table.Clear();
        }
    }
}

class Business(IDao dao) : IBusiness
{
    // invoeging van een array artikelen: alles of niets
    public void InsertArticlesInTransaction(Article[] articles)
    {
        // begin van de transactie, opgeslagen in de thread-lokale gegevens
        var transaction = new Transaction();
        ThreadContext.Transaction.Value = transaction;
        try
        {
            foreach (Article article in articles)
            {
                // de laag [dao] vindt de transactie in de thread
                dao.InsertArticle(article);
                // gesimuleerde verwerking, waardoor andere threads de ruimte krijgen om tussenbeide te komen
                Thread.Sleep(200);
            }
            transaction.Commit();
            Console.WriteLine($"[{Thread.CurrentThread.Name}] [business] transaction {transaction.Number} committed");
        }
        catch
        {
            transaction.Rollback();
            Console.WriteLine($"[{Thread.CurrentThread.Name}] [business] transaction {transaction.Number} rolled back");
            throw;
        }
        finally
        {
            // de thread heeft geen lopende transactie meer
            ThreadContext.Transaction.Value = null;
        }
    }

    // invoeging van een array artikelen zonder transactie
    public void InsertArticlesOutOfTransaction(Article[] articles)
    {
        foreach (Article article in articles)
        {
            dao.InsertArticle(article);
        }
    }

    public List<Article> GetAllArticles() => dao.GetAllArticles();
    public void DeleteAllArticles() => dao.DeleteAllArticles();
}

    8.10.3. Conclusie

    Het voorgaande voorbeeld liet de waarde zien van threadlokale gegevens voor transactiebeheer. Het moet niet ongewijzigd worden overgenomen. .NET biedt dit mechanisme kant-en-klaar met de klasse [System.Transactions.TransactionScope]: een „ambient” transactie, toegankelijk via [Transaction.Current], waaraan databaseverbindingen automatisch deelnemen. Frameworks zoals Entity Framework Core beheren transacties ook zonder dat de code van de laag [dao] zich daarmee hoeft bezig te houden. En in de huidige webapplicaties, die asynchroon zijn, wordt deze contextinformatie gedragen door [AsyncLocal<T>] in plaats van door threadlokale gegevens.
