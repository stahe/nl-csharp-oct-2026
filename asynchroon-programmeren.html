    9. Asynchroon programmeren

    Het vorige hoofdstuk introduceerde threads: we kunnen meerdere stukken code „tegelijkertijd” uitvoeren, ze synchroniseren en taken aan de threadpool toewijzen. Dit hoofdstuk, dat niet in de cursus van 2008 stond, behandelt een verwant maar ander vraagstuk: hoe schrijft u een programma dat lang wacht (op de schijf, het netwerk of een database) zonder tijdens die wachttijden threads te blokkeren. Het antwoord in .NET ligt in twee sleutelwoorden van de taal C#, [async] en [await], en in één type, [Task]. Ze zijn tegenwoordig overal: in de volgende hoofdstukken gebruiken we ze om databases te benaderen ([OpenAsync], [ExecuteReaderAsync], [ToListAsync], [SaveChangesAsync]), om TCP-servers ([AcceptTcpClientAsync]), webclients ([HttpClient]) en webservices met ASP.NET Core te schrijven.

    Alle voorbeelden in dit hoofdstuk zijn single-file-applicaties ([async-01.cs], [async-02.cs]…) die worden uitgevoerd met [dotnet run async-NN.cs] in de map [09-async]. Veel ervan meten tijdsduren met een stopwatch ([Stopwatch]): de weergegeven milliseconden verschillen van de ene uitvoering tot de andere en van de ene machine tot de andere (de voorbeelden zijn uitgevoerd op een machine met twee processors). Het gaat om de ordes van grootte: 1 seconde of 3 seconden, 300 ms of 0 ms.

    9.1. Waarom asynchroniteit

    9.1.1. Bewerkingen die wachten

    Een programma verricht twee soorten werk:

    • rekenwerk, dat de processor bezighoudt: een lijst sorteren, een belasting berekenen, een tekst analyseren;
    • invoer/uitvoer (I/O), die in wezen bestaat uit wachten op een randapparaat: een bestand van schijf lezen, een verzoek naar een webserver sturen en op het antwoord wachten, een SQL-query uitvoeren op een databaseserver.

    De ordes van grootte verschillen sterk. Een processor voert enkele miljarden instructies per seconde uit. Een leesbewerking op een schijf (SSD) duurt in de orde van een tiende milliseconde; een heen-en-terugreis over een lokaal netwerk duurt een fractie van een milliseconde; een heen-en-terugreis naar een server aan de andere kant van het land duurt enkele tientallen milliseconden; en een enigszins complexe SQL-query kan soms enkele seconden duren. Tijdens deze wachttijden had de processor miljoenen instructies kunnen uitvoeren.

    Wanneer een programma een regel leest via een netwerkverbinding met een synchrone (blokkerende) methode, is de thread die deze leesbewerking uitvoert geblokkeerd: hij doet niets, maar bestaat nog steeds. Hij neemt geheugen in beslag (zijn stack, in de orde van een megabyte), is bekend bij het besturingssysteem en, vooral, is niet meer beschikbaar voor ander werk. In een klein consoleprogramma dat één ding tegelijk doet, is dit geen probleem. Het is veel lastiger in twee situaties:

    • op een server: elke client die door een geblokkeerde thread wordt bediend, houdt die thread vast. In de cursus van 2008 werd dit al uitgelegd in de conclusie van de bespreking van de asynchrone TCP-client: als de threadpool N threads heeft en alle N threads een blokkerende bewerking uitvoeren, zijn er geen threads meer beschikbaar voor een nieuwe client. Een moderne webserver handelt duizenden gelijktijdige verzoeken af met slechts enkele tientallen threads: dat is mogelijk omdat zijn threads nooit op I/O worden geblokkeerd;
    • in een grafische gebruikersinterface: één enkele thread – de UI-thread – handelt klikken af en tekent vensters opnieuw. Als die door een download wordt geblokkeerd, loopt het venster vast.

    Asynchroniteit houdt in dat de I/O-bewerking wordt gestart, de thread vrijgegeven terwijl de bewerking loopt (de hardware en het besturingssysteem hebben hem niet nodig om gegevens over te brengen), en het werk wordt hervat zodra de bewerking is voltooid, eventueel op een andere thread:

    • In [1]start thread T1 de I/O en blijft geblokkeerd totdat die klaar is;
    • in [2]start thread T1 de I/O en keert terug naar de threadpool, waar hij andere verzoeken kan afhandelen. Wanneer de I/O-bewerking is voltooid, meldt het systeem dit aan .NET, dat een thread uit de pool – T2 (of T1, als die beschikbaar is) – het vervolg van de verwerking laat uitvoeren.

    // waarom asynchroniteit: 100 bewerkingen die elk één seconde wachten
// (een wachttijd simuleert I/O: schijf lezen, netwerkverzoek, SQL-query…)
using System.Diagnostics;

const int nbOperations = 100;
Console.WriteLine($"{nbOperations} operations of one second, {Environment.ProcessorCount} processors");

// 1 - één thread per bewerking, elke thread is tijdens het wachten geblokkeerd
var stopwatch = Stopwatch.StartNew();
var threads = new Thread[nbOperations];
for (int i = 0; i < nbOperations; i++)
{
    threads[i] = new Thread(() => Thread.Sleep(1000));
    threads[i].Start();
}
Display("1 - one thread per operation", ProcessThreads());
foreach (var thread in threads)
{
    thread.Join();
}
Display("    end");

// 2 - de bewerkingen worden aan de threadpool toevertrouwd, maar blokkeren die
stopwatch.Restart();
var tasks = new Task[nbOperations];
for (int i = 0; i < nbOperations; i++)
{
    tasks[i] = Task.Run(() => Thread.Sleep(1000));
}
Display("2 - thread pool, blocking waits", ProcessThreads());
Task.WaitAll(tasks);
Display("    end");

// 3 - asynchrone wachttijden: tijdens het wachten is er geen thread geblokkeerd
stopwatch.Restart();
for (int i = 0; i < nbOperations; i++)
{
    tasks[i] = Task.Delay(1000);
}
Display("3 - asynchronous waits", ProcessThreads());
await Task.WhenAll(tasks);
Display("    end");

// aantal threads van het proces, een halve seconde nadat de bewerkingen zijn gestart
int ProcessThreads()
{
    if (stopwatch.ElapsedMilliseconds < 500)
    {
        Thread.Sleep(500 - (int)stopwatch.ElapsedMilliseconds);
    }
    using var process = Process.GetCurrentProcess();
    return process.Threads.Count;
}

// weergave van de verstreken tijd en, indien opgegeven, van het aantal threads
void Display(string message, int? nbThreads = null)
{
    string threadsInfo = nbThreads is null ? "" : $", {nbThreads,3} threads in the process";
    Console.WriteLine($"{message,-42} : {stopwatch.ElapsedMilliseconds,5} ms{threadsInfo}");
}

    Opmerkingen:

    • regels 8–21: de oplossing uit de cursus van 2008, één thread per bewerking. Elke thread voert [Thread.Sleep(1000)] uit: hij is een seconde geblokkeerd. De 100 wachttijden verlopen gelijktijdig en het hele proces duurt precies één seconde (regel 4), maar ten koste van 100 extra threads: het proces heeft nu meer dan 100 threads (regel 3). Bij 10.000 bewerkingen zouden 10.000 threads nodig zijn;
    • regels 23–31: de bewerkingen worden gedelegeerd aan de threadpool ([Task.Run]), die in het vorige hoofdstuk is geïntroduceerd. De pool begint met evenveel threads als er processors zijn (hier 2) en voegt er slechts geleidelijk meer toe wanneer ze allemaal bezet zijn, omdat hij ervan uitgaat dat zijn threads rekenwerk verrichten en dat er niet veel meer threads nodig zijn dan processors. Maar hier rekenen de threads niet: zij zijn inactief. De bewerkingen wachten op een vrije thread, en het hele proces duurt… meer dan twintig seconden (regel 6). Dit heet „thread pool starvation”, de meest voorkomende tekortkoming van servers die threadpools met blokkerende I/O combineren;
    • regels 34–41: de wachttijden zijn asynchroon ([Task.Delay] in plaats van [Thread.Sleep]). Tijdens het wachten is er geen enkele thread geblokkeerd: een systeemtimer maakt .NET na een seconde wakker. Het hele proces duurt een seconde en het aantal threads neemt niet toe (de threads die op regel 7 worden getoond, zijn die welke de pool tijdens stap 2 heeft aangemaakt; zij zijn inactief);
    • regel 51: [Process.GetCurrentProcess()] geeft toegang tot het proces dat op dat moment wordt uitgevoerd; de eigenschap [Threads] is de verzameling van zijn threads (die van .NET en die van het systeem).

    Laten we de les onthouden: om te wachten mag u geen thread blokkeren. Asynchroniteit maakt I/O niet sneller; zij maakt het mogelijk veel I/O-bewerkingen tegelijk met weinig threads af te handelen en de threads die de applicatie nodig heeft beschikbaar te houden (de GUI-thread, de threads in de pool van een server).

    9.1.2. Drie opeenvolgende modellen

    .NET kende drie manieren om asynchrone code te schrijven. De eerste twee komen nog voor in legacycode en oudere artikelen, dus het is nuttig ze te herkennen.

    Model
    Oorsprong
    Principe
    APM („Asynchronous Programming Model”)
    .NET 1.0 (2002)
    een paar methoden: [BeginXxx] en [EndXxx]. [BeginXxx] start de bewerking en ontvangt een callbackmethode ([AsyncCallback]); de callbackmethode, die aan het einde van de bewerking door een thread uit de pool wordt uitgevoerd, roept [EndXxx] aan om het resultaat of de uitzondering op te halen. Voorbeeld: [Socket.BeginConnect] / [EndConnect], gebruikt door de asynchrone TCP-client uit de cursus van 2008.
    EAP („Event-based Asynchronous Pattern”)
    .NET 2.0 (2005)
    een methode [XxxAsync] die de bewerking start en een gebeurtenis [XxxCompleted] die wordt geactiveerd wanneer de bewerking is voltooid. Voorbeelden: [WebClient.DownloadStringAsync] en [DownloadStringCompleted], de klasse [BackgroundWorker] (gebeurtenissen [DoWork], [ProgressChanged], [RunWorkerCompleted]) die in de cursus van 2008 is behandeld.
    TAP („Task-based Asynchronous Pattern”)
    .NET 4.0 (2010), C# 5 (2012)
    een methode [XxxAsync] die een taak ([Task] of [Task<T>]) teruggeeft die de lopende bewerking vertegenwoordigt. De aanroepende code wacht op de taak met het sleutelwoord [await]. Dit is het huidige model, het enige dat in de rest van de cursus wordt gebruikt.

    De patronen APM en EAP hebben hetzelfde gebrek: de code wordt in stukken gehakt. Wat vanzelf leest als „verbinden, dan lezen, dan tonen” wordt een methode die de verbinding start, een callbackmethode die het lezen start en nog een callbackmethode die de gegevens toont; variabelen moeten tussen deze methoden worden gedeeld, uitzonderingen worden op verschillende plaatsen afgehandeld, en een eenvoudige lus („lees zolang er gegevens zijn”) wordt een callbackmethode die zichzelf recursief aanroept, zoals de leesmethode ([lecture]) uit de cursus van 2008. Met het patroon TAP, samen met [async] en [await], kunt u asynchrone code schrijven die eruitziet als synchrone code.

    // dezelfde TCP-client geschreven met het APM-model uit 2008 en daarna met het huidige TAP-model
using System.Net;
using System.Net.Sockets;
using System.Text;

const int port = 27500;
// een minimale server, uitgevoerd door een thread: hij bedient twee clients en stopt dan
var listener = new TcpListener(IPAddress.Loopback, port);
listener.Start();
var server = new Thread(() =>
{
    for (int i = 1; i <= 2; i++)
    {
        using Socket service = listener.AcceptSocket();
        // de server doet er even over om te antwoorden
        Thread.Sleep(500);
        service.Send(Encoding.UTF8.GetBytes($"Hello client no. {i}"));
    }
    listener.Stop();
});
server.Start();
Display("start of the program");

// 1 - het APM-model (Asynchronous Programming Model): BeginXxx / EndXxx en callbackmethoden
var end = new ManualResetEventSlim(false);
byte[] buffer = new byte[1024];
var client = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
// we starten de verbinding en geven de methode op die na afloop wordt aangeroepen
client.BeginConnect(IPAddress.Loopback, port, Connected, client);
Display("APM: connection launched, the program goes on");
// de hoofdthread heeft niets meer te doen: hij wacht op het signaal van de laatste callbackmethode
end.Wait();

// callbackmethode nr. 1: de verbinding is tot stand gebracht
void Connected(IAsyncResult result)
{
    // we halen het object op dat als laatste parameter aan BeginConnect is doorgegeven
    var socket = (Socket)result.AsyncState!;
    // we beëindigen de bewerking (bij een mislukking gooit EndConnect de exception)
    socket.EndConnect(result);
    Display("APM: connected, read launched");
    // we starten het lezen van het antwoord van de server met een andere callbackmethode
    socket.BeginReceive(buffer, 0, buffer.Length, SocketFlags.None, Received, socket);
}

// callbackmethode nr. 2: er zijn gegevens binnengekomen
void Received(IAsyncResult result)
{
    var socket = (Socket)result.AsyncState!;
    int nbBytes = socket.EndReceive(result);
    Display($"APM: received [{Encoding.UTF8.GetString(buffer, 0, nbBytes)}]");
    socket.Close();
    // we waarschuwen de hoofdthread
    end.Set();
}

// 2 - het TAP-model (Task-based Asynchronous Pattern): XxxAsync en await
using (var client2 = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp))
{
    await client2.ConnectAsync(IPAddress.Loopback, port);
    Display("TAP: connected, read launched");
    int nbBytes = await client2.ReceiveAsync(buffer);
    Display($"TAP: received [{Encoding.UTF8.GetString(buffer, 0, nbBytes)}]");
}
server.Join();

// weergave voorafgegaan door het nummer van de thread die haar uitvoert
static void Display(string message)
{
    Console.WriteLine($"[thread {Environment.CurrentManagedThreadId,2}] {message}");
}

De laatste twee parameters zijn de callbackmethode die aan het einde van de verbinding moet worden aangeroepen, [Connected], en een willekeurig object dat de callbackmethode terugvindt in de eigenschap [AsyncState] van haar parameter [IAsyncResult]: in dit geval de socket zelf;
      • regel 32: de hoofdthread heeft niets meer te doen. Om te voorkomen dat het programma eindigt voordat de uitwisseling is voltooid, wacht hij op een signaal dat door de laatste callbackmethode wordt gegeven: een object [ManualResetEventSlim], waarvan de methode [Wait] de thread die haar aanroept blokkeert totdat een andere thread de methode [Set] aanroept (dit is een lichtgewicht versie van de barrières [AutoResetEvent] die we bij threads hebben gezien);
      • regels 35–43: de callbackmethode van de verbinding. Zij moet [EndConnect] aanroepen met de ontvangen parameter: deze aanroep beëindigt de bewerking en zou een uitzondering genereren als de verbinding was mislukt. Daarna start zij de leesbewerking met [BeginReceive], waarbij zij een tweede callbackmethode opgeeft, [Received];
      • regels 47–54: de lees-callback haalt het aantal ontvangen bytes op met [EndReceive], toont het bericht, sluit de socket en geeft de hoofdthread vrij;
      • de resultaten laten zien dat de callbackmethoden worden uitgevoerd door een andere thread dan de hoofdthread (een thread uit de pool, niet thread 1);
    • regels 57–65: dezelfde client volgens het TAP-model. [ConnectAsync] en [ReceiveAsync] geven taken terug, en [await] wacht tot ze klaar zijn zonder de thread te blokkeren: de code leest van boven naar beneden als synchrone code; de variabelen zijn gewone lokale variabelen; er zijn geen callbackmethoden of signalen om te beheren. De thread die de rest van de code uitvoert, is doorgaans niet langer thread 1: waarom dat zo is, leggen we uit in de paragraaf „Welke thread voert de rest uit?”;
    • regel 68: elke weergave wordt voorafgegaan door het nummer van de thread die haar uitvoert, [Environment.CurrentManagedThreadId].

    U hoeft het APM-patroon niet te onthouden. Als u een oudere bibliotheek moet gebruiken die alleen dit patroon biedt, zet de methode [Task.Factory.FromAsync] een paar [BeginXxx] / [EndXxx] om in een methode die een [Task] teruggeeft; en in de paragraaf over [TaskCompletionSource] zullen we zien hoe u een gebeurtenisgebaseerde API (EAP-model) in een taak omzet.

    9.2. Taken: Task en Task<T>

    Een taak is een object dat een lopende of voltooide bewerking vertegenwoordigt:

    • [Task] vertegenwoordigt een bewerking die geen resultaat teruggeeft;
    • [Task<T>] vertegenwoordigt een bewerking die een resultaat van het type [T] zal teruggeven. [Task<T>] is afgeleid van [Task].

    Een taak is geen thread. Een taak kan door een thread uit de pool worden uitgevoerd (zoals bij taken die met [Task.Run] zijn gemaakt), maar veel taken worden door geen enkele thread uitgevoerd: de taak die [Task.Delay(1000)] teruggeeft, wordt na een seconde eenvoudigweg door een timer „voltooid”; de taak die [ReceiveAsync] teruggeeft, wordt voltooid wanneer het systeem meldt dat er gegevens zijn binnengekomen. Een taak is een belofte van een resultaat, waarnaar kan worden gevraagd (is hij klaar? is hij geslaagd?) en waarop kan worden gewacht.

// 1 - Task.Run vertrouwt een verwerking toe aan de threadpool en geeft een taak Task<T> terug
Task<long> task1 = Task.Run(() =>
{
    // een berekening van enkele tienden van een seconde
    long sum = 0;
    for (int i = 1; i <= 200_000_000; i++)
    {
        sum += i % 7;
    }
    return sum;
});
Console.WriteLine($"task1 launched, status: {task1.Status}");
// await onderbreekt het programma tot het einde van de taak en geeft het resultaat ervan terug
long result = await task1;
Console.WriteLine($"task1 finished, status: {task1.Status}, result: {result}");

// 2 - Task.Delay geeft een taak terug die na een vertraging eindigt, zonder een thread te bezetten
Task task2 = Task.Delay(300);
Console.WriteLine($"task2 launched, status: {task2.Status}");
await task2;
Console.WriteLine($"task2 finished, status: {task2.Status}");

// 3 - taken die al klaar zijn
Task<int> task3 = Task.FromResult(42);
Task task4 = Task.CompletedTask;
Console.WriteLine($"task3: status {task3.Status}, result {await task3} ; task4: status {task4.Status}");

// 4 - een taak die mislukt: await gooit haar exception opnieuw
Task<int> task5 = Task.Run(() => int.Parse("abc"));
try
{
    await task5;
}
catch (FormatException e)
{
    Console.WriteLine($"task5: status {task5.Status}, {e.GetType().Name}: {e.Message}");
}

// 5 - de blokkerende vormen Wait() en Result: de huidige thread is tijdens het wachten geblokkeerd
Task<string> task6 = Task.Run(() =>
{
    Thread.Sleep(300);
    return "done";

    • regels 4–12: [Task.Run] wijst een functie toe aan de threadpool en geeft onmiddellijk een taak terug die de uitvoering ervan vertegenwoordigt.     • regel 14: de eigenschap [Status] geeft de toestand van de taak terug. Direct na het starten wacht de taak hier tot een thread uit de pool haar oppakt ([WaitingToRun]); afhankelijk van de belasting van de machine kunt u ook [Running] (wordt uitgevoerd) zien;
    • regel 16: [await task1] wacht tot de taak klaar is zonder de thread te blokkeren en geeft het resultaat terug, dat hier van het type [long] is. De expressie [await t] is van het type [T] als [t] van het type [Task<T>] is, en heeft geen waarde als [t] van het type [Task] is;
    • regel 20: [Task.Delay(300)] geeft een taak terug die over 300 ms voltooid zal zijn. In die tijd is er geen enkele thread bezet. Dit is het asynchrone equivalent van [Thread.Sleep(300)]. De toestand ervan, [WaitingForActivation], betekent „wachten op een externe gebeurtenis”;
    • regels 26–27: [Task.FromResult(42)] geeft een taak terug die al is voltooid met het resultaat 42, terwijl [Task.CompletedTask] een taak teruggeeft die al is voltooid zonder resultaat. Deze worden gebruikt wanneer een methode een taak moet teruggeven maar het resultaat al heeft (bijvoorbeeld een waarde uit de cache);
    • regels 31–36: een taak waarvan de functie een uitzondering genereert, eindigt met de toestand [Faulted]. De uitzondering wordt in de taak bewaard en [await] genereert haar opnieuw; zij wordt opgevangen met een gewone [try / catch];
    • regels 42–48: [Wait()] wacht tot de taak klaar is door de huidige thread te blokkeren, en de eigenschap [Result] geeft het resultaat van een [Task<T>] terug en blokkeert daarbij eveneens de thread als de taak niet klaar is. Dit zijn de vormen waarbij op de thread wordt gewacht uit het vorige hoofdstuk ([Join]). Ze zijn te vermijden: ze hebben alle nadelen van blokkerende I/O, verpakken uitzonderingen in een [AggregateException] (regel 56) en kunnen in een grafische applicatie een deadlock veroorzaken. Gebruik ze alleen in de zeldzame gevallen waarin u weet dat de taak al is voltooid;
    • regel 51: [ContinueWith] koppelt een continuatie aan een taak: een functie die wordt uitgevoerd wanneer de taak is voltooid. De continuatie ontvangt de voltooide taak en geeft hier een geheel getal terug: dat levert een nieuwe taak op, [Task<int>]. Zo werd asynchrone code geschreven met .NET 4.0, vóór [await]; [await] berust op een vergelijkbaar mechanisme (het registreren van een vervolg dat aan het einde van de taak wordt uitgevoerd), dat door de compiler op een veiligere manier wordt geïmplementeerd. [ContinueWith] wordt nauwelijks nog rechtstreeks gebruikt;
    • regels 54–56: de Booleaanse eigenschappen [IsCompleted] (beëindigd, op welke manier dan ook), [IsCompletedSuccessfully] (met succes beëindigd), [IsFaulted] (beëindigd door een uitzondering), [IsCanceled] (geannuleerd), en de eigenschap [Exception], van het type [AggregateException], die de uitzondering(en) van de taak bevat.

Het zijn de awaited bewerkingen ([Task.Delay], asynchrone I/O) die werkelijk asynchroon zijn.

Task<int> CountSugarsAsync(int count)

    var machine = new CountSugarsMachine { count = count, state = 0 };

class CountSugarsMachine
{
    public int count, i, state;               // de lokale variabelen worden velden
    public TaskCompletionSource<int> Source = new();
    public Task<int> ResultTask => Source.Task;

    public void Advance()
    {
        if (state == 0) { i = 1; }             // eerste doorloop: begin van de lus
        else { Console.WriteLine($"  sugar no. {i}"); i++; }   // hervatting na de await
        if (i <= count)
        {
            state = 1;
            // we vragen om aan het einde van de vertraging te worden aangeroepen en geven dan de besturing terug
            Task.Delay(200).GetAwaiter().OnCompleted(Advance);
            return;
        }
        Source.SetResult(count);               // einde van de methode: de taak is voltooid
    }
}

    9.6. Annulering en time-outs

    9.6.1. CancellationTokenSource en CancellationToken

    Een langlopende asynchrone bewerking moet annuleerbaar zijn: de gebruiker heeft op [Cancel] geklikt, een client van een webserver heeft de verbinding verbroken, de applicatie is afgesloten of een time-out is overschreden. .NET gebruikt hiervoor een coöperatief mechanisme met twee objecten:

    • een [CancellationTokenSource] (annuleerbron), in handen van de code die besluit te annuleren. De methode [Cancel()] vraagt om annulering; [CancelAfter(delay)] vraagt er automatisch om na een time-out;
    • een [CancellationToken] (annuleertoken), verkregen via de eigenschap [Token] van de bron en als parameter doorgegeven aan annuleerbare bewerkingen. De bewerking controleert het token ([IsCancellationRequested]) of laat het een uitzondering genereren als om annulering is gevraagd ([ThrowIfCancellationRequested()]), en geeft het door aan de bewerkingen die ze aanroept.

    Het mechanisme is coöperatief: niemand onderbreekt een bewerking met geweld (de methode [Thread.Abort] uit de cursus van 2008 is in het huidige .NET verouderd: ze genereert alleen nog een [PlatformNotSupportedException]); de bewerking stopt uit zichzelf, op een punt waar dat netjes kan. Volgens afspraak eindigt een geannuleerde bewerking met het genereren van een [OperationCanceledException] en heeft haar taak de status [Canceled].

{

        {
            // gooit OperationCanceledException als de annulering is aangevraagd
            token.ThrowIfCancellationRequested();
        }
        sum += i % 7;
    }
    return sum;
}

// een verwerking beperkt tot [timeout] milliseconden, die ook door de aanroeper kan worden gestopt
async Task ProcessWithTimeoutAsync(string name, int duration, int timeout, CancellationToken stop)
{
    // de gekoppelde bron wordt geannuleerd zodra een van de twee oorzaken zich voordoet
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(stop);
    linked.CancelAfter(timeout);
    try
    {
        Display($"3 - {await QueryAsync(name, duration, linked.Token)}");
    }
    catch (OperationCanceledException) when (stop.IsCancellationRequested)
    {
        Display($"3 - {name} : stopped at the caller's request");
    }
    catch (OperationCanceledException)
    {
        Display($"3 - {name} : timeout of {timeout} ms exceeded");
    }
}

    • ze wordt geproduceerd met een [async]-methode, die [IAsyncEnumerable<T>] retourneert en zowel [await] als [yield return] bevat;

class RateService
{
    private readonly Dictionary<string, decimal> cache = [];
    public int NbServerAccesses { get; private set; }
    public int NbCacheAccesses { get; private set; }

    // ValueTask<decimal>: geen Task-allocatie wanneer het resultaat in de cache staat
    public ValueTask<decimal> ReadRateAsync(string code)
    {
        if (cache.TryGetValue(code, out decimal rate))
        {
            // snel en synchroon pad: het resultaat is al bekend
            NbCacheAccesses++;
            return ValueTask.FromResult(rate);
        }
        // traag en asynchroon pad: de server moet worden bevraagd
        return new ValueTask<decimal>(ReadServerRateAsync(code));
    }

    private async Task<decimal> ReadServerRateAsync(string code)
    {
        NbServerAccesses++;
        // simuleert het bevragen van een externe server
        await Task.Delay(300);
        decimal rate = code switch
        {
            "EUR" => 1m,
            "USD" => 1.17m,
            "GBP" => 0.87m,
            _ => throw new ArgumentException($"unknown currency: {code}"),
        };
        cache[code] = rate;
        return rate;
    }
}

    9.10.2. ConfigureAwait en de synchronisatiecontext

    Het programma [async-05.cs] liet zien dat in de console de rest van een methode na een [await] wordt uitgevoerd door een willekeurige thread uit de pool. Dat is niet het geval in een grafische applicatie (Windows Forms, WPF, MAUI). Een grafische component mag alleen door de UI-thread worden bewerkt: de cursus van 2008 moest vanuit zijn callback-methoden [listBoxEvts.Invoke(...)] gebruiken om de update door die thread te laten uitvoeren. Met [await] is dat niet meer nodig: de interfacethread heeft een synchronisatiecontext ([SynchronizationContext.Current] is niet [null]), die [await] opslaat; aan het einde van het wachten wordt de rest van de methode aan deze context teruggegeven en dus door de interfacethread uitgevoerd. We kunnen schrijven:

    Deze terugkeer naar de oorspronkelijke context kost iets en brengt een risico mee: als code de interfacethread blokkeert terwijl ze op een taak wacht ([task.Result]) en die taak diezelfde thread nodig heeft om zijn resterende code uit te voeren, wachten beide eindeloos op elkaar („deadlock”). Dit is de belangrijkste reden voor de regel „geen [.Result]”.

    De methode [ConfigureAwait(false)] draagt [await] op niet naar de oorspronkelijke context terug te keren: [await stream.ReadAsync(buffer).ConfigureAwait(false);]. De rest van de code wordt dan door een thread uit de pool uitgevoerd. De aanbevelingen zijn als volgt:

    • gebruik in de code van een algemene bibliotheek (die geen grafische gebruikersinterface afhandelt en niet weet wie haar aanroept) [ConfigureAwait(false)] bij elke [await]: dat is iets efficiënter en voorkomt deadlocks als een onzorgvuldige aanroeper [.Result] gebruikt;
    • in applicatiecode (grafische gebruikersinterface, consoleprogramma, ASP.NET Core-applicatie) wordt het niet geschreven. Consoleprogramma's en ASP.NET Core-applicaties hebben sowieso geen synchronisatiecontext: [ConfigureAwait(false)] maakt daar geen verschil.

    De voorbeelden in deze cursus, die applicaties zijn, gebruiken [ConfigureAwait] niet.

// zet de gebeurtenissen MeasureTaken van de thermometer om in een taak
static Task<double> WaitForTemperatureAsync(Thermometer thermometer, double threshold, CancellationToken token)
{
    // de bron van een taak die we zelf voltooien
    var source = new TaskCompletionSource<double>(TaskCreationOptions.RunContinuationsAsynchronously);
    // de registratie bij het annuleringstoken, vrij te geven zodra de taak klaar is
    CancellationTokenRegistration registration = default;
    // de gebeurtenishandler voltooit de taak zodra de drempel is bereikt
    void OnMeasure(object? sender, double temperature)
    {
        if (temperature >= threshold && source.TrySetResult(temperature))
        {
            thermometer.MeasureTaken -= OnMeasure;
            registration.Dispose();
        }
    }
    thermometer.MeasureTaken += OnMeasure;
    // een annuleringsverzoek voltooit de taak met de status Canceled
    registration = token.Register(() =>
    {
        if (source.TrySetCanceled(token))
        {
            thermometer.MeasureTaken -= OnMeasure;
        }
    });
    // de taak wordt meteen teruggegeven; zij wordt later voltooid
    return source.Task;
}

    9.11.2. Producent/consument: System.Threading.Channels

    Het vorige hoofdstuk introduceerde het patroon producent/consument met de verzameling [BlockingCollection<T>]: producerende threads plaatsen elementen in een wachtrij en consumerende threads halen ze eruit; [Take] (of de enumeratie [GetConsumingEnumerable]) blokkeert een consument zolang de wachtrij leeg is, terwijl [Add] een producent blokkeert zolang een begrensde wachtrij vol is. Deze wachtbewerkingen blokkeren threads. Channels in de namespace [System.Threading.Channels] (.NET Core 3.0) bieden dezelfde dienst met asynchrone wachtbewerkingen:

    • [Channel.CreateBounded<T>(capacity)] maakt een begrensd kanaal, [Channel.CreateUnbounded<T>()] maakt een onbegrensd kanaal;
    • de eigenschap [Writer] ([ChannelWriter<T>]) wordt door producenten gebruikt: [WriteAsync] publiceert een item (en wacht asynchroon tot er ruimte beschikbaar komt), [TryWrite] probeert het direct toe te voegen, [Complete] geeft aan dat er geen elementen meer komen;
    • De eigenschap [Reader] ([ChannelReader<T>]) wordt door consumenten gebruikt: [ReadAsync] haalt een element op, terwijl [ReadAllAsync] een asynchrone stroom van alle elementen retourneert, die eindigt wanneer het kanaal door [Complete] is gesloten en leeg is.

using System.Threading.Channels;

// de producent: één bestelling per 50 ms
async Task ProduceAsync(ChannelWriter<int> writer, int nbOrders)
{
    for (int i = 1; i <= nbOrders; i++)
    {
        await Task.Delay(50);
        // TryWrite laat de bestelling meteen vallen als er plaats is in het kanaal
        if (writer.TryWrite(i))
        {
            Display($"P  : order {i} dropped");
        }
        else
        {
            // kanaal vol: WriteAsync wacht (zonder een thread te blokkeren) tot er een plek vrijkomt
            Display($"P  : channel full, order {i} waits");
            await writer.WriteAsync(i);
            Display($"P  : order {i} dropped");
        }
    }
    // er wordt niets meer geschreven: de consumenten verlaten hun lus
    writer.Complete();
    Display("P  : end of the production");
}

// een consument: het verwerken van een bestelling duurt 400 ms
async Task ConsumeAsync(string name, ChannelReader<int> reader)
{
    // ReadAllAsync geeft een asynchrone stream terug die eindigt wanneer het kanaal gesloten en leeg is
    await foreach (int order in reader.ReadAllAsync())
    {
        Display($"{name} : processing of order {order}");
        await Task.Delay(400);
    }
    Display($"{name} : no more orders");
}

void Display(string message)
{
    Console.WriteLine($"{stopwatch.ElapsedMilliseconds,5} ms : {message}");
}

    9.12. Tijd: PeriodicTimer en TimeProvider

    Twee recente klassen completeren de hulpmiddelen rond tijd:

// leest de belastingschijven (limit:coeffR:coeffN, decimale punt)
static async Task<TaxBracket[]> LoadBracketsAsync(string file, CancellationToken token)
{
    string[] lines = await File.ReadAllLinesAsync(file, token);
    return [.. lines.Where(l => l.Trim() != "").Select(TaxBracket.Parse)];
}

// leest de belastingplichtigen (gehuwd kinderen salaris), berekent hun belasting en schrijft de resultaten
static async Task<int> CalculateTaxesAsync(TaxBracket[] brackets, string input, string output, CancellationToken token)
{
    int nbLines = 0;
    await using var writer = new StreamWriter(output);
    await foreach (string line in File.ReadLinesAsync(input, token))
    {
        string[] fields = line.Split(' ', StringSplitOptions.RemoveEmptyEntries);
        string result = fields switch
        {
            [var m, var c, var s] when m is "y" or "n" && int.TryParse(c, out int children) && children >= 0
                                       && int.TryParse(s, out int salary) && salary >= 0
                => $"tax = {CalculateTax(brackets, m == "y", children, salary)} €",
            _ => "incorrect line",
        };
        await writer.WriteLineAsync($"{line,-12} : {result}");
        nbLines++;
    }
    return nbLines;
}

// de belastingberekening (schaal van 2004 op inkomen van 2003, behouden voor de oefening)
static int CalculateTax(TaxBracket[] brackets, bool married, int nbChildren, int salary)
{
    decimal shares = married ? nbChildren / 2m + 2 : nbChildren / 2m + 1;
    if (nbChildren >= 3)
    {
        shares += 0.5m;
    }
    decimal income = 0.72m * salary;
    decimal quotient = income / shares;
    // de eerste schijf waarvan de limiet het gezinsquotiënt overschrijdt, anders de laatste
    TaxBracket bracket = brackets.FirstOrDefault(t => quotient <= t.Limit, brackets[^1]);
    return (int)(bracket.CoeffR * income - bracket.CoeffN * shares);
}

// een belastingschijf
readonly record struct TaxBracket(decimal Limit, decimal CoeffR, decimal CoeffN)

    public static TaxBracket Parse(string line)
    {
        string[] fields = line.Split(':');
        return new TaxBracket(decimal.Parse(fields[0], CultureInfo.InvariantCulture),
                                decimal.Parse(fields[1], CultureInfo.InvariantCulture),
                                decimal.Parse(fields[2], CultureInfo.InvariantCulture));
    }
}

    9.14. De gouden regels

    Laten we de regels van asynchroon programmeren met .NET samenvatten:

    • async helemaal door: een methode die op een asynchrone bewerking wacht, wordt zelf asynchroon ([async Task]), en dat geldt ook voor haar aanroepers, helemaal terug tot het toegangspunt ([Main] asynchroon, gebeurtenishandler, controlleractie in ASP.NET Core). Asynchrone code combineren met blokkerende wachtbewerkingen doet de voordelen van asynchronie teniet;
    • gebruik geen [.Result], [.Wait()] of [Task.WaitAll] op een onvoltooide taak: gebruik in plaats daarvan [await], [Task.WhenAll], [Task.WhenAny] of [Task.WhenEach]. Deze blokkerende vormen leggen een thread stil en kunnen in grafische applicaties blijvende deadlocks veroorzaken;
    • gebruik geen [Thread.Sleep] in asynchrone code: gebruik in plaats daarvan [await Task.Delay(...)];
    • schrijf geen [async void]-methoden, behalve in GUI-gebeurtenishandlers; een asynchrone methode gebruikt [Task] of [Task<T>] (in uitzonderlijke gevallen [ValueTask<T>]);
    • de naam van een asynchrone methode eindigt op [Async]: [CalculateTaxesAsync], [ReadRateAsync];
    • een annuleerbare asynchrone methode ontvangt een [CancellationToken] als laatste parameter en geeft die door aan alle asynchrone bewerkingen die ze aanroept; een geannuleerde bewerking eindigt met een [OperationCanceledException];
    • [Task.Run] is gereserveerd voor berekeningen die u op de achtergrond wilt uitvoeren (bijvoorbeeld om een GUI-thread niet te blokkeren). Verpak een synchrone I/O-bewerking niet in [Task.Run] om haar „asynchroon te maken”: gebruik de [XxxAsync]-versie van de bewerking;
    • eerst starten, dan wachten: om meerdere onafhankelijke bewerkingen gelijktijdig uit te voeren, start u ze allemaal en wacht u er daarna op met [Task.WhenAll]; om het aantal bewerkingen te beperken, gebruikt u [Parallel.ForEachAsync] of een channel;
    • [ConfigureAwait(false)] wordt gebruikt in bibliotheken, niet in applicaties;
    • op een gestarte taak moet worden gewacht (of ze moet expliciet worden genegeerd met [_ =], waarbij u haar uitzonderingen afhandelt): een vergeten taak verbergt haar uitzonderingen en kan door het einde van het programma worden onderbroken.
