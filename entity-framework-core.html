    11. Entity Framework Core

    Het vorige hoofdstuk liet zien hoe een .NET-applicatie met een database communiceert via een ADO.NET-connector: een verbinding wordt geopend, SQL-opdrachten worden geschreven, de resultaatrijen worden kolom voor kolom gelezen en gekopieerd naar objecten. Dit kopieerproces – van rijen naar objecten en van objecten naar de [INSERT]-, [UPDATE]- en [DELETE]-opdrachten – is repetitief. Het kan worden geautomatiseerd met een hulpmiddel: een ORM (Object-Relational Mapper). Dit hoofdstuk introduceert Entity Framework Core van Microsoft (EF Core).

    De cursus uit 2008 ging niet in op ORM: aan het slot van het hoofdstuk over databases noemde die slechts „frameworks van derden voor gegevenstoegang” (NHibernate, iBatis) en LINQ. Entity Framework verscheen enkele maanden later (in 2008, met .NET 3.5 SP1), en in 2012 wijdde de auteur er een cursus aan met de titel „Introduction to Entity Framework 5 Code First Through Examples”. Dit hoofdstuk is geheel nieuw. Het bouwt voort op de voorbeelddatabase met artikelen uit Hoofdstuk 10 en sluit af met versie 7 van de applicatie voor de belastingberekening, waarvan de [dao]-laag EF Core gebruikt.

    11.1. Wat is een ORM?

    11.1.1. Objecten en tabellen

    Een C#-applicatie werkt met objecten: een artikel heeft een naam, een prijs en een voorraad; een bestelling heeft een klant en een lijst met orderregels, die elk naar een artikel verwijzen. Een relationele database slaat dezelfde informatie op in tabellen: één rij in de tabel [articles] per artikel, één rij in de tabel [orders] per bestelling, waarbij de relaties tussen rijen worden uitgedrukt door refererende sleutels. De twee werelden sluiten niet helemaal op elkaar aan:

    • een object verwijst rechtstreeks naar andere objecten ([order.Client]); een rij bevat de waarde van de primaire sleutel van een andere rij ([ClientId]);
    • een object kan een verzameling bevatten ([order.Lines]); een tabel bevat alleen enkelvoudige waarden; de verzameling wordt voorgesteld door de rijen van een andere tabel die naar de bestelling verwijzen;
    • de C#-typen ([string], [decimal], [DateOnly], [bool]) en de SQL-typen ([varchar(30)], [decimal(10,2)], [date], [tinyint(1)]) zijn niet dezelfde;
    • objecten worden bevraagd met C# (en LINQ) en tabellen met SQL.

    Een ORM overbrugt de twee werelden. We definiëren de afbeelding tussen klassen en tabellen (het model) eenmalig; daarna zorgt de ORM voor:

    • het vertalen van in C# geschreven LINQ-query's naar SQL-[SELECT]-opdrachten;
    • het aanmaken van objecten uit de gelezen rijen (dit heet materialisatie);
    • het bijhouden van de gelezen objecten en het detecteren van de objecten die zijn gewijzigd, toegevoegd of verwijderd;
    • het genereren van de [INSERT]-, [UPDATE]- en [DELETE]-opdrachten die deze wijzigingen in de database doorvoeren;
    • en, indien nodig, het aanmaken en bijwerken van het databaseschema (tabellen, kolommen, indexen) op basis van de klassen.

    De architectuur van een applicatie die EF Core met MySQL gebruikt, is als volgt:

    • [1]: de applicatie. De [dao]-laag ervan communiceert niet langer met een ADO.NET-connector maar met EF Core, via een [DbContext]-object en LINQ-query's;
    • [2]: EF Core, onafhankelijk van het DBMS: model, vertaling van LINQ-query's, wijzigingen bijhouden (change tracking), migraties;
    • [3]: de provider van EF Core die specifiek is voor het DBMS (hier Pomelo voor MySQL): deze kent het SQL-dialect van het DBMS en de kolomtypen ervan;
    • [4]: de ADO.NET-connector voor het DBMS, die uit Hoofdstuk 10 (MySqlConnector): EF Core vervangt ADO.NET niet; het gebruikt het;
    • [5]: het DBMS.

    11.1.2. EF Core en Entity Framework 6

    Er zijn twee producten met de naam Entity Framework:

    • Entity Framework 6 (EF 6), het oorspronkelijke product, ontworpen voor .NET Framework op Windows (sinds versie 6.3 werkt het ook op .NET Core en de opvolgers daarvan). Het wordt nog onderhouden, maar wordt niet meer actief doorontwikkeld;
    • Entity Framework Core, een volledige herschrijving die in 2016 met .NET Core werd uitgebracht. Het draait op alle .NET-platforms (Windows, Linux, macOS) en is de versie die alle nieuwe functies krijgt. Het versienummer volgt dat van .NET: EF Core 8 met .NET 8, EF Core 9 met .NET 9, EF Core 10 met .NET 10.

    Voor een nieuwe applicatie gebruiken we EF Core. Beide producten hebben vergelijkbare API's ([DbContext], [DbSet<T>], LINQ, migraties), dus wat hier wordt gezegd blijft grotendeels ook voor EF 6 gelden.

    11.1.3. Providers

    EF Core benadert een DBMS via een provider, die in een NuGet-pakket wordt verspreid. Microsoft levert de providers voor SQL Server, SQLite en Azure Cosmos DB; de overige worden geschreven door de DBMS-leveranciers of door de community: [Npgsql.EntityFrameworkCore.PostgreSQL] voor PostgreSQL, [Oracle.EntityFrameworkCore] voor Oracle, [Pomelo.EntityFrameworkCore.MySql] en [MySql.EntityFrameworkCore] (van Oracle) voor MySQL. Wij gebruiken Pomelo, de meest gebruikte MySQL-provider, die gebaseerd is op de connector [MySqlConnector] uit Hoofdstuk 10.

    Een provider wordt gecompileerd voor een specifieke versie van EF Core: Pomelo 9 werkt met EF Core 9, en versies van Pomelo verschijnen vaak enkele maanden na die van EF Core. De cursus gebruikt EF Core 9.0.0 en Pomelo 9.0.0, op .NET 10. Deze combinatie werkt: EF Core 9 richt zich op .NET 8 ([net8.0]), en een bibliotheek die voor .NET 8 is gecompileerd, werkt zonder aanpassing op .NET 10. De overstap naar EF Core 10 gebeurt door de versienummers van de pakketten te wijzigen; de code in dit hoofdstuk zou dan zonder aanpassing moeten werken, op enkele kleine details in de gegenereerde SQL na. In de paragraaf over LINQ komen we echter een kleine incompatibiliteit tegen tussen EF Core 9 en de C# 14-compiler.

    11.1.4. Code First en Database First

    Het EF Core-model (de afbeelding tussen klassen en tabellen) kan op twee manieren worden opgebouwd:

    • Code First: u schrijft de C#-klassen en EF Core leidt het databaseschema ervan af, dat het zelf kan aanmaken en vervolgens kan bijwerken naarmate de applicatie evolueert (migraties). Dit is de aanpak in dit hoofdstuk en in de cursus van de auteur uit 2012;
    • Database First: de database bestaat al en u genereert de klassen uit het schema ervan met de opdracht [dotnet ef dbcontext scaffold]. Dit is de aanpak voor applicaties die met een bestaande database moeten werken. De gegenereerde code lijkt op wat we met de hand zouden schrijven.

    namespace First;

// een artikel van de winkel: een gewone C#-klasse, zonder verband met EF Core
public class Article
{
    // primaire sleutel (volgens conventie: de eigenschap met de naam Id)
    public int Id { get; set; }
    // de overige kolommen van de tabel
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
    public int CurrentStock { get; set; }
    public int MinimumStock { get; set; }

    // weergave
    public override string ToString() => $"[{Id}, {Name}, {Price}, {CurrentStock}, {MinimumStock}]";
}
    • Regel 4: een gewone C#-klasse. Ze erft niet van een klasse van EF Core en heeft geen attributen; dit heet een POCO (Plain Old CLR Object);
    • Regel 7: de eigenschap [Id] wordt de primaire sleutel van de tabel. Dit is een conventie van EF Core: een eigenschap met de naam [Id] (of [ArticleId], de klassenaam gevolgd door [Id]) is de primaire sleutel. Omdat de eigenschap van het type integer is, worden de waarden ervan door het DBMS gegenereerd (kolom [AUTO_INCREMENT] van MySQL);
    • regels 9–12: elke publieke lees-/schrijfeigenschap wordt een kolom met dezelfde naam. De eigenschap [Name] wordt geïnitialiseerd met een lege tekenreeks om de compiler tevreden te stellen (nullable typen ingeschakeld: een eigenschap van het type [string] mag niet [null] blijven);
    • regel 15: een handige weergave van het artikel.

    using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Logging;

namespace First;

// de context: de toegangspoort tot de database [efarticles]
public class ArticlesContext : DbContext
{
    // de tabel articles
    public DbSet<Article> Articles => Set<Article>();

    // configuratie van de context: DBMS, verbindingsreeks, log
    protected override void OnConfiguring(DbContextOptionsBuilder options)
    {
        const string connection = "Server=localhost;Port=3306;Database=efarticles;User=root;Password=";
        options
            // de MySQL-provider en de versie van de server
            .UseMySql(connection, new MySqlServerVersion(new Version(8, 0, 36)))
            // weergave van de SQL-instructies die naar de server worden gestuurd
            .LogTo(Console.WriteLine, [DbLoggerCategory.Database.Command.Name], LogLevel.Information);
    }
}
    • Regel 7: de klasse [DbContext] komt uit EF Core. Een [ArticlesContext]-object vertegenwoordigt een werksessie met de database: het opent de verbinding wanneer dat nodig is, bewaart de entiteiten die het heeft gelezen en kan wijzigingen daarin opslaan;
    • Regel 10: een [DbSet<Article>] vertegenwoordigt de tabel met artikelen. Hier worden LINQ-query's uitgevoerd en artikelen toegevoegd of verwijderd. De eigenschap is gedefinieerd als een expression-bodied member die [Set<Article>()] aanroept: elke [DbSet<T>] die in de context wordt gedeclareerd, voegt het type [T] toe aan het model;
    • regel 13: de methode [OnConfiguring] wordt door EF Core aangeroepen wanneer de context voor het eerst wordt gebruikt, om deze te configureren;
    • regel 15: de verbindingsreeks, dezelfde als in Hoofdstuk 10: server, poort, database, gebruikersnaam en wachtwoord (leeg voor de Laragon-gebruiker [root]);
    • regel 18: de context gebruikt de Pomelo-provider. De tweede parameter geeft de serverversie van MySQL op: de gegenereerde SQL hangt daarvan af, omdat bepaalde functies alleen in recente versies beschikbaar zijn. Laragon levert MySQL 8; we geven versie 8.0.36 op. Pomelo biedt ook [ServerVersion.AutoDetect(connection)], dat de server bevraagt om de versie vast te stellen. Dat is handig, maar het kost een extra verbinding telkens wanneer een context wordt geconfigureerd, en de gegenereerde SQL hangt dan af van de aangetroffen server. Door een versie expliciet op te geven, is het gedrag van de applicatie reproduceerbaar;
    • regel 20: de methode [LogTo] geeft EF Core de opdracht zijn logboek te schrijven met de methode [Console.WriteLine]. We behouden alleen de berichtcategorie [DbLoggerCategory.Database.Command] – die van uitgevoerde SQL-opdrachten – op het niveau [LogLevel.Information]. Zonder dit filter is het logboek zeer uitgebreid. Het bekijken van de SQL die naar de server wordt gestuurd, is de beste manier om te begrijpen wat EF Core doet: dat doen we in alle voorbeelden.

    using First;

// een EF Core-context: hij wordt aan het einde van het programma vrijgegeven (verbinding inbegrepen)
using var context = new ArticlesContext();

// de database wordt verwijderd en daarna opnieuw aangemaakt vanuit het C#-model

// toevoegen van drie artikelen

context.Articles.Add(new Article { Name = "pump", Price = 10, CurrentStock = 10, MinimumStock = 2 });
context.Articles.Add(new Article { Name = "bow", Price = 600, CurrentStock = 4, MinimumStock = 1 });
Console.WriteLine("--- SaveChanges");
int nbRows = context.SaveChanges();
Console.WriteLine($"{nbRows} row(s) inserted");

    Console.WriteLine(article);

    Toelichting:

    • Elke SQL-opdracht wordt voorafgegaan door een kop van twee regels: het gebeurtenistype ([CommandExecuted]), de uitvoeringstijd en de parameters van de opdracht;
    • Regel 4: [EnsureDeleted] heeft de database verwijderd, die al bestond (het programma was al eerder uitgevoerd);
    • regels 7–20: [EnsureCreated] heeft de database aangemaakt, er de tekenset [utf8mb4] (de volledige Unicode-set van MySQL) aan toegekend en vervolgens de tabel [Articles] aangemaakt op basis van de entiteit [Article]: de tabelnaam is die van de contexteigenschap [DbSet], de kolommen zijn genoemd naar de eigenschappen en de kolom [Id] is de primaire sleutel met een gegenereerde waarde ([AUTO_INCREMENT]). De parameterwaarden zijn gemaskeerd ('?'): het zijn applicatiegegevens, die vertrouwelijk kunnen zijn.     We hebben geen enkele SQL-opdracht en geen enkele code voor het lezen van kolommen geschreven: dat is precies het doel van een ORM. We zien ook dat dit de noodzaak om SQL te begrijpen niet wegneemt: om te bepalen of de gegenereerde SQL juist en doeltreffend is, moet u weten hoe u die leest.

    11.3. Het model

    EF Core bouwt zijn model in drie stappen op uit entiteiten:

    • eerst past het zijn conventies toe;
    • het vult ze aan of corrigeert ze met de annotaties (attributen) die op de entiteiten zijn aangebracht;
    • ten slotte past het de in C# geschreven configuratie toe in de methode [OnModelCreating] van de context: de fluent API.

    11.3.1. De conventies

    De belangrijkste hebben we in het eerste voorbeeld gezien:

    • elke publieke eigenschap met een [get]-getter en een [set] (of [init])-setter wordt opgeslagen in een kolom met dezelfde naam;
    • de eigenschap [Id] of [<Entity>Id] is de primaire sleutel; als het een integer is, worden de waarden door het DBMS gegenereerd;
    • de tabelnaam is die van de eigenschap [DbSet] van de context (of, bij gebreke daarvan, die van de klasse);
    • een eigenschap van een nullable type ([int?], [DateOnly?], [string?]) levert een kolom [NULL] op; een eigenschap van een niet-nullable type ([int], [decimal], [string] wanneer nullable referentietypen zijn ingeschakeld) levert een kolom [NOT NULL] op;
    • een eigenschap die naar een andere entiteit verwijst, of een verzameling entiteiten, definieert een relatie (daar komen we later op terug).

    Nullable referentietypen (C# 8, in de cursusprojecten ingeschakeld met [<Nullable>enable</Nullable>] ) hebben invloed op het model: EF Core leest de nullability-annotaties die door de compiler worden gegenereerd. namespace Ef.Tools;

// een compacte log van de SQL-instructies die door EF Core worden uitgevoerd
public static class SqlLog
{
    // een extensielid (C# 14) van het type DbContextOptionsBuilder
    extension(DbContextOptionsBuilder options)
    {
        // options.WithSqlLog(): toont elke uitgevoerde SQL-instructie
        public DbContextOptionsBuilder WithSqlLog() => options.LogTo(Filter, Display);
    }

    // de geselecteerde gebeurtenissen: SQL-opdracht uitgevoerd of mislukt, begin en einde van de transacties
    private static bool Filter(EventId id, LogLevel level) =>
        id == RelationalEventId.CommandExecuted || id == RelationalEventId.CommandError
        || id == RelationalEventId.TransactionStarted
        || id == RelationalEventId.TransactionCommitted || id == RelationalEventId.TransactionRolledBack;

    // weergave van een gebeurtenis
    private static void Display(EventData data)
    {
        switch (data)
        {
            case CommandExecutedEventData command:
                DisplayCommand(command.Command);
                break;
            case CommandErrorEventData error:
                DisplayCommand(error.Command);
                Console.WriteLine("    SQL> -- command failed");
                break;
            case TransactionEventData when data.EventId == RelationalEventId.TransactionStarted:
                Console.WriteLine("    SQL> -- start of transaction");
                break;
            case TransactionEventData when data.EventId == RelationalEventId.TransactionCommitted:
                Console.WriteLine("    SQL> -- transaction committed (COMMIT)");
                break;
            case TransactionEventData:
                Console.WriteLine("    SQL> -- transaction rolled back (ROLLBACK)");
                break;
        }
    }

    // weergave van de SQL-instructie, ingesprongen, en daarna van de parameters ervan
    private static void DisplayCommand(DbCommand command)
    {
        // de lege regels worden genegeerd
        foreach (string line in command.CommandText.Split('\n').Select(l => l.TrimEnd()).Where(l => l != ""))
        {
            Console.WriteLine("    SQL> " + line);
        }
        if (command.Parameters.Count > 0)
        {
            var parameters = command.Parameters.Cast<DbParameter>()
                .Select(p => $"{(p.ParameterName.StartsWith('@') ? "" : "@")}{p.ParameterName}={p.Value}");
            Console.WriteLine($"    SQL> -- parameters: {string.Join(", ", parameters)}");
        }
    }
}

    • de opdracht [INSERT], gevolgd door een [SELECT] van de gegenereerde sleutel, is omsloten door een transactie (regels 13–20): de opdracht bevat twee SQL-opdrachten die samen moeten slagen. We komen later terug op transacties;
    • de afzonderlijke opdrachten [UPDATE] en [DELETE] worden niet door een transactie omsloten. Ze worden voorafgegaan door [SET AUTOCOMMIT = 1], een sessie-instelling van MySQL (elke opdracht wordt gecommit zodra die is uitgevoerd) die de provider voor de zekerheid herstelt. Deze instelling heeft geen effect op een expliciet geopende transactie, zoals we zullen zien.

    11.5.2. De toestanden van een entiteit

    Het bijhouden van wijzigingen is gebaseerd op de toestand van elke entiteit, een waarde uit de [EntityState]-enumeratie:

    Toestand
    Betekenis
    [Detached]
    Het object wordt niet door de context bijgehouden (aangemaakt met [new] en nog niet toegevoegd, of uit de database verwijderd)
    [Added]
    Het object is aan de context toegevoegd ([Add]): [SaveChanges] voegt het in de database in
    [Unchanged]
    Het object is uit de database gelezen (of opgeslagen) en is sindsdien niet gewijzigd
    [Modified]
    Ten minste één eigenschap is gewijzigd: [SaveChanges] stuurt een [UPDATE]-opdracht
    [Deleted]
    Het object is gemarkeerd voor verwijdering ([Remove]): [SaveChanges] stuurt een [DELETE]-opdracht

    Let op de werkcyclus met EF Core: entiteiten worden gelezen, als gewone objecten gewijzigd, toegevoegd en verwijderd, waarna [SaveChanges] wordt aangeroepen, dat alle benodigde opdrachten in één batch naar de database stuurt. De context fungeert als „unit of work”. Een context is een lichtgewicht object dat bedoeld is voor een korte levensduur: een werkeenheid, zoals een HTTP-verzoek in een webapplicatie. Dezelfde context wordt niet gedurende de hele levensduur van een applicatie gebruikt, omdat hij steeds meer bijgehouden entiteiten zou verzamelen.

    • regel 30: [FirstOrDefault] wordt [LIMIT 1]. Dit is de regel die Hoofdstuk 10 handmatig toepaste met geparametriseerde queries;
    • regels 35–36: de aggregaties [Count] en [Sum] worden door het DBMS berekend ([COUNT(*)], [SUM(...)]): alleen het resultaat wordt overgedragen, niet de rijen. [COALESCE(..., 0.0)] geeft 0 terug als de tabel leeg is, net als [Sum] van LINQ;
    • Regels 42–45: de .NET-methoden die EF Core kent, worden vertaald naar SQL: [a.Name.StartsWith("b")] wordt [LIKE 'b%'], en [names.Contains(a.Name)], dat verwijst naar een lijst in het geheugen, wordt [IN ('bow', 'pump', 'racket')] (regel 35).     • regels 57–60: paginering, om een lange lijst pagina voor pagina weer te geven.     • regel 61: deze projectie bevat een geïnterpoleerde tekenreeks, die EF Core niet naar SQL vertaalt.     • regels 69–71: EF Core kan de aanroep van een willekeurige methode van het programma niet vertalen: het kent de code ervan niet en zou, zelfs als het die kende, niet noodzakelijk weten hoe het die in SQL moet schrijven.     • regel 78: [AsEnumerable()] draagt de query over van [IQueryable<T>] naar [IEnumerable<T>]: het voorgaande deel wordt naar SQL vertaald (hier het lezen van de hele tabel) en het volgende deel wordt door LINQ in het geheugen uitgevoerd.     11.6.2. IQueryable en expressiebomen

    Hoe kan dezelfde lambda in C# op een lijst worden uitgevoerd en op een [DbSet] naar SQL worden vertaald? Hoofdstuk 7 gaf het antwoord: een [DbSet<T>] implementeert de interface [IQueryable<T>], waarvan de methoden [Where], [OrderBy], [Select]... geen delegates ([Func<T, bool>]) maar expressiebomen ([Expression<Func<T, bool>>]) ontvangen. De compiler transformeert de lambda [a => a.CurrentStock < a.MinimumStock] tot een gegevensstructuur die de lambda beschrijft („vergelijking [<] van eigenschap [CurrentStock] en eigenschap [MinimumStock] van parameter [a]”); EF Core doorloopt deze structuur en produceert de equivalente SQL. Een methode zoals [Rules.OutOfStock] verschijnt in de boom alleen als methodeaanroep, waarvan de code niet kan worden geanalyseerd: vandaar de fout.

    Operatoren kunnen worden samengesteld: een query kan in fasen worden opgebouwd, waarbij elke fase een nieuwe [IQueryable<T>] teruggeeft, en pas de uiteindelijke uitvoering ([ToList], [First], [Count], [foreach]...) stuurt een SQL-opdracht:

    11.6.3. Een incompatibiliteit tussen EF Core 9 en C# 14

    In het programma [Linq] was de lijst [names] gedeclareerd als type [List<string>] in plaats van [string[]], met een opmerking die naar deze paragraaf verwijst. Met een array compileert de query [context.Articles.Where(a => names.Contains(a.Name))] wel, maar ze mislukt tijdens runtime met een [InvalidOperationException]-fout („An exception was thrown while attempting to evaluate a LINQ query parameter expression”). C# 14 heeft namelijk de conversie van een array naar [ReadOnlySpan<T>] (het type dat in Hoofdstuk 5 is geïntroduceerd) tot een impliciete taalconversie gemaakt, die ook geldt voor het object waarop een extensiemethode wordt aangeroepen. Voor een array verwijst de aanroep [names.Contains(...)] dus nu naar de extensiemethode [MemoryExtensions.Contains(ReadOnlySpan<T>, T)] in plaats van naar [Enumerable.Contains(IEnumerable<T>, T)]: dit blijkt uit onderzoek van de expressieboom van de lambda, en hetzelfde programma gecompileerd in C# 13 ([<LangVersion>13</LangVersion>]) vindt [Enumerable.Contains] en werkt. EF Core 9, dat vóór C# 14 is uitgebracht, herkent deze methode niet: het probeert de conversie van de array naar [ReadOnlySpan<string>] te evalueren om er een SQL-parameter van te maken, wat mislukt (de interne uitzondering is een [ArgumentException] die door de interpreter van de expressieboom wordt opgeworpen). EF Core 10, dat samen met C# 14 is uitgebracht, ondersteunt deze syntaxis. Met EF Core 9 kunt u het probleem omzeilen door een lijst te gebruiken, zoals hier, of door [((IEnumerable<string>)names).Contains(a.Name)] te schrijven. Dit is het enige probleem dat we in dit hoofdstuk tegenkomen bij het gebruik van EF Core 9 met .NET 10.

    • regels 56–71: een klant, zijn bestelling en de twee orderregels ervan worden met één aanroep van [Add] toegevoegd.     • Regels 79–80: standaard laadt EF Core alleen de gevraagde entiteit. De navigatie-eigenschappen [Client] en [Lines] van de gelezen bestelling zijn niet gevuld (regel 41): [Client] is gelijk aan [null] (ondanks de niet-nullable declaratie, vandaar de [?.]-operator) en de lijst met orderregels is leeg. EF Core ondersteunt lazy loading: de navigatie-eigenschap wordt automatisch geladen bij de eerste lezing. Dit moet expliciet worden ingeschakeld (pakket [Microsoft.EntityFrameworkCore.Proxies], navigatie-eigenschappen [virtual]); wij gebruiken het niet omdat het databasetoegang verbergt;
    • Regels 87–89: eager loading. [Include(c => c.Client)] geeft de opdracht om voor elke bestelling de klant te laden; [Include(c => c.Lines)] laadt de orderregels en [ThenInclude(l => l.Product)] laadt het product van elke regel. Alles wordt geladen door één enkele [SELECT]-query, met joins (regels 45–51). De weergave toont beide bestellingen en hun regels;
    • regel 106: het expliciet laden. We laden de verzameling producten van een categorie die al is gelezen: een tweede query, [SELECT], leest de producten waarvan de refererende sleutel overeenkomt met die van de categorie.     • Regels 114–116: navigatie-eigenschappen worden gebruikt in LINQ-query's, zonder [Include]: [p.Tags.Any(...)] wordt een subquery [EXISTS] op de koppeltabel (regels 72–76), en [p.Category.Name] wordt een join;
    • regels 125–126: een berekening over twee relaties – het bedrag van elke bestelling – die volledig door het DBMS met een subquery wordt uitgevoerd (regels 81–84);
    • regels 135–138: een groepering (group by). De categorie [diving], die geen producten heeft, komt niet voor: de join met de categorietabel is een inner join ([INNER JOIN]).

    Het zogeheten „N+1-queryprobleem” vormt een risico voor elke gebruiker van een ORM. Stel dat we voor elke bestelling de naam van de klant willen tonen en dat we de bestellingen zonder [Include] lezen en vervolgens voor elke bestelling de klant ophalen via expliciet laden (of via lazy loading, wat op hetzelfde neerkomt zonder dat we het merken): dan voeren we één query uit voor de N bestellingen en daarna N queries, één per bestelling. Bij duizend bestellingen levert dat duizend en één roundtrips naar de server op, terwijl één roundtrip had volstaan. De oplossingen zijn die in het voorbeeld: [Include], of beter nog een projectie ([Select]) die alleen de relevante gegevens ophaalt. Het SQL-logboek helpt het probleem te herkennen: dezelfde query die talloze keren wordt herhaald.

    11.8. Migraties

    11.8.1. Het principe

    Tot nu toe is de database aangemaakt door [EnsureCreated], nadat ze was verwijderd door [EnsureDeleted]. Dat is onmogelijk voor een draaiende applicatie: de database bevat gegevens die bewaard moeten blijven wanneer het model evolueert (een nieuwe kolom, een nieuwe tabel). Bovendien kan [EnsureCreated] alleen een database aanmaken die nog niet bestaat: als de database al met tabellen bestaat, doet het niets, ook al is het model gewijzigd.

    Migraties voorzien in deze behoefte. Een migratie is een C#-klasse, gegenereerd door de tool [dotnet ef], die de overgang van de ene versie van het model naar de volgende beschrijft: de methode [Up] past de wijziging toe (een tabel aanmaken, een kolom toevoegen), terwijl de methode [Down] die ongedaan maakt. De database bevat een tabel met de naam [__EFMigrationsHistory], waarin EF Core de migraties vastlegt die erop zijn toegepast; zo weet het welke nog moeten worden toegepast.

Daarom gebruiken ASP.NET Core-applicaties consequent de asynchrone methoden van EF Core.

    11.10.2. Optimistische gelijktijdigheid

    Twee gebruikers lezen hetzelfde artikel, waarvan de voorraad 10 is. De eerste gebruiker verkoopt één stuk en werkt de voorraad bij naar 9. De tweede gebruiker, die de voorraad vóór deze wijziging heeft gelezen, verkoopt drie stuks en werkt de voorraad bij naar 7: de verkoop van de eerste gebruiker gaat verloren. Dit is het probleem van verloren updates.

    Een oplossing zou zijn de rij te vergrendelen gedurende de hele bewerking van elke gebruiker („pessimistische” gelijktijdigheid): dit blokkeert andere gebruikers, soms lange tijd. EF Core implementeert optimistische gelijktijdigheid: er wordt niets vergrendeld, maar op het moment van de commit controleert het systeem of de rij sinds het lezen niet is gewijzigd. Hiervoor worden een of meer eigenschappen aangewezen als concurrency tokens: EF Core voegt de voorwaarde „het token heeft nog de gelezen waarde” toe aan de [WHERE]-clausule van de opdrachten [UPDATE] en [DELETE] . Als de opdracht geen enkele rij wijzigt, betekent dit dat een andere gebruiker de rijen al heeft verwerkt: EF Core genereert dan een [DbUpdateConcurrencyException].

    11.12. Context en dependency injection

    De vorige voorbeelden maakten hun contexten met [new]. In een gelaagde applicatie, en in alle ASP.NET Core-applicaties, worden contexten gemaakt door de dependency-injectiecontainer die in hoofdstuk 6 is geïntroduceerd. EF Core biedt hiervoor twee extensiemethoden van [IServiceCollection]:

    • [AddDbContext<T>(options => ...)] registreert de context [T] met een „scoped” levensduur: de container maakt een context per scope, levert deze aan alle services binnen die scope die erom vragen en geeft de context aan het einde van de scope vrij. In een webapplicatie wordt voor elk HTTP-verzoek een scope gemaakt: elk verzoek heeft zijn eigen context, wat overeenkomt met de werkeenheid van de context;
    • [AddDbContextFactory<T>(options => ...)] registreert een contextfactory, [IDbContextFactory<T>], waarvan de methode [CreateDbContext] bij elke aanroep een nieuwe context maakt. Deze wordt gebruikt in langlopende services (singletons), die niet gedurende de hele levensduur van de applicatie dezelfde context kunnen behouden, en bij parallelle verwerking, waarvoor één context per taak nodig is.

    In beide gevallen ontvangt de lambda een [DbContextOptionsBuilder] en configureert deze de context zoals [OnConfiguring] dat deed; de context moet een constructor hebben die een [DbContextOptions<T>] accepteert, zoals die van de klasse [ArticlesContext] .

    11.14. Conclusie: ADO.NET, Dapper of EF Core?

    We hebben nu twee manieren om toegang tot een database te krijgen: ADO.NET (hoofdstuk 10) en EF Core (dit hoofdstuk). Er is een derde, tussenliggende methode die veel wordt gebruikt: Dapper, een kleine bibliotheek (een „micro-ORM”) die extensiemethoden toevoegt aan de ADO.NET-verbinding. Deze methoden voeren een met de hand geschreven SQL-query uit en zetten de rijen in het resultaat automatisch om in objecten: [connection.Query<Article>("SELECT * FROM articles WHERE Price > @price", new { price = 200 })]. U schrijft de SQL en Dapper zorgt voor het koppelen van de kolommen aan eigenschappen.

     
    Sterke punten
    Zwakke punten
    ADO.NET
    Volledige controle over SQL; prestaties; geen afhankelijkheden
    veel repetitieve code (parameters, kolommen lezen); SQL in strings, niet gecontroleerd door de compiler
    Dapper
    SQL met de hand geschreven, maar zonder de kopieercode; prestaties vergelijkbaar met ADO.NET
    Geen wijzigingen bijhouden of genereren van [INSERT]/[UPDATE]; geen migraties
    EF Core
    LINQ-query's die door de compiler worden gecontroleerd; wijzigingen bijhouden; relaties; migraties; onafhankelijk van het DBMS
    een extra laag om te begrijpen; gegenereerde SQL die gemonitord moet worden; minder geschikt voor complexe bulkverwerking

    De volgende richtlijnen kunnen worden voorgesteld:

    • EF Core is geschikt voor de meeste beheerapplicaties: een model van onderling verbonden entiteiten, bewerkingen voor het lezen en bijwerken van entiteiten en een schema dat met de applicatie meegroeit. Het is de standaardkeuze voor ASP.NET Core-applicaties;
    • ADO.NET of Dapper is geschikt wanneer u nauwkeurige controle wilt over de uitgevoerde SQL: complexe rapportagequery's, stored procedures, het verwerken van zeer grote volumes of een bestaande database met een schema dat slecht past bij een objectgeoriënteerd model;
    • Deze benaderingen kunnen worden gecombineerd: een applicatie kan voor het grootste deel EF Core gebruiken en met de hand geschreven SQL-code, met [FromSql], [SqlQuery] of Dapper, voor een paar kritieke query's. EF Core geeft ook toegang tot de ADO.NET-verbinding die het gebruikt ([context.Database.GetDbConnection()]).

    Hoe dan ook: kennis van ORM maakt het niet overbodig om SQL en de werking van het DBMS te begrijpen: het logboek van uitgevoerde SQL-opdrachten, dat we in dit hoofdstuk steeds hebben weergegeven, is het belangrijkste hulpmiddel om te controleren wat EF Core daadwerkelijk doet.

    Voor meer informatie is de documentatie van Microsoft uitgebreid: Entity Framework Core. De Pomelo-provider is gedocumenteerd in de bijbehorende repository: Pomelo.EntityFrameworkCore.MySql.
